# 理念索引与设计入口

这里按要作出的判断组织阅读路径：理解业务模型，按问题范围确定服务协作与应用内部职责，再检查行为与表达。绿地视角帮助检验既有安排，演进方法帮助落实调整。按当前问题选读，具体原则各有唯一归属。

## 内容地图

| 当前问题 | 进入 |
|---|---|
| 如何结合业务、系统与应用架构理解问题 | [Skill 入口](../SKILL.md#先建立全局视角再决定改动落点) |
| 核心概念、关系和主流程是否充分，新概念是否成立 | [业务建模](modeling.md) |
| 服务边界、权威数据、通信与失败恢复是否合理 | [跨服务的职责与协作](modularity.md#跨服务的职责与协作) |
| 应用内部哪层能力不足，改动如何分派 | [按职责分派改动](modularity.md#按职责分派改动) |
| 模块边界、目录、依赖与复用如何组织 | [模块化](modularity.md) |
| 如何重新审视现状、比较方案并安排调整 | [从问题到调整](evolution.md#从问题到调整)、[绿地视角](evolution.md#绿地视角) |
| 如何用长期场景、MR 复盘和机制化约束推进演进 | [演进](evolution.md#长期方向) |
| 既定职责下，控制流与行为契约是否正确清楚 | [行为](behavior.md) |
| 命名、文档、注释与日志如何表达设计 | [表达](expression.md) |
| 如何评审模型、职责与具体实现 | [架构与代码评审](review.md) |
| 需要具体反例与正例 | [案例索引](examples/README.md) |

## 内容归属约定

- 每条原则只有一个事实来源；入口和 checklist 只链接，不复制解释。
- 概念与流程归 modeling，服务协作、分层与代码组织归 modularity，设计审视和调整方法归 evolution，局部实现归 behavior，设计表达与文档组织归 expression。
- 相邻主题用简短说明与链接连接；评审归 review，真实 case 归 [examples](examples/README.md)。新内容先找对应职责，归属不清时调整现有组织。
