## 先定义问题

- 架构先回答“要解决什么问题”，再回答“用什么方案”。
- 不要只拿脑中第一个方案开工；至少能说清备选方案和取舍理由。
- 真正决定架构选择的往往是性能、扩展性、可维护性、团队能力、发布时间等非功能性需求。

## 识别既有设计

既有设计不是最早的代码形状，也不是作者脑中的一次性想法，而是系统当前仍然成立、持续承担
复杂度控制职责的核心模型、边界和依赖关系。分析时依次看：

1. 核心对象是什么；
2. 关键边界在哪里，谁负责业务编排、资源操作、协议或存储适配；
3. 主要查询键和资源归属是什么；
4. 创建、复用、更新、回收的主生命周期是什么；
5. 复杂度原本靠统一状态机、稳定模型、清晰分层还是固定资源 shape 压住。

## 判断顺序

1. 先定义原始问题和非功能性约束；
2. 再识别既有模型、边界、查询键和生命周期；
3. 用长期场景与绿地视角判断是增加 case，还是旧模型已经失效；
4. 再决定概念收束、模块边界和依赖方向；
5. 最后检查接口、复杂度、复用和实现形状。

## 内容归属约定

- 每条原则只有一个事实来源；README 和 checklist 只链接，不复制解释。
- 抽象原则进入本目录，真实 case 进入 [[../examples/README|examples]]。
- 新内容先按模型、边界、演进、可维护性选择 owner；找不到归属时先调整结构，不新增“其它”章节。
