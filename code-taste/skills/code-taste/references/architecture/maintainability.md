# 架构可维护性判断

## 复杂度

- 架构的首要价值是控制复杂度，不是展示技术栈。
- 复杂度是增量引入的；每次改动都应减少混乱，至少不能继续放大。
- review 设计时追问：这会让系统更容易变更，还是更难变更？
- 模块持续增长到无法单独理解时，应按 owner、职责和变化原因拆分。长度是复核信号，不是架构目标；
  函数、参数和局部可读性的判断归 [代码 Review](../code/review.md)。

## 代码归属与文件组织

- 先确定逻辑属于哪个已有类型或模块，再选择文件落点。属于某个类型的少量行为，优先放在该类型或
  同主题实现附近；例如 `Command.Summary()` 通常与 `Command` 放在一起，无须另建摘要文件。
- 抽取函数、方法与拆出文件是两次判断。局部 helper 可以在原文件中表达职责；一个新功能、命名清晰
  或可以单独测试，都不自动产生独立文件的必要性。
- 独立文件应带来可指出的收益：一组可单独理解的职责、需要隔离的依赖或平台编译条件、稳定的公开
  入口，或明显减少主流程的阅读负担。沿用项目已有组织惯例，避免按每次需求不断追加小文件。
- 比较放在一起与分开的阅读和修改成本：若常见改动总要同时打开两处，拆出的方法也必须结合原文件
  才能理解，优先合并或移回所属实现。若独立边界清楚，小文件同样合理，不设方法数或行数下限。
- Go 同包拆文件不会增加封装边界；TypeScript 拆文件可能增加 import/export。不要为拆文件而扩大
  helper 的可见性，也不要把目录、文件数量当成职责清晰度。

## 复用判断

- 写任何“看起来通用”的逻辑前，按成本递增勘探：
  1. 搜本仓同名 / 近义符号；
  2. 查框架、common 库、既有 utils 是否原生提供；
  3. 看同模块近邻是否已有契合的 helper 或模式。
- 能复用且语义契合就复用；已有语义或边界不同、复用会逼出模糊接口时才新写。
- 复用的目标是降低长期维护成本，不是短期少写几行。
- 区分真实重复和意外重复；意图不同的相似代码可以保持分开。
- 错误抽象往往比重复代码更糟，抽象失败时宁可退回明确重复。
