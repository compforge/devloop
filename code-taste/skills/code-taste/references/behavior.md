# 行为：控制流、职责与契约

## 控制与逻辑：分离关注点

- 程序 = Logic + Control。Logic 表达业务判断与变换，Control 决定这些逻辑何时、以什么顺序、分支、
  并发或重试方式执行；业务逻辑与流程控制、协议适配、线程异步、调度胶水必须分离。
- 好的抽象会固化稳定、重复的控制骨架，并显式暴露持续变化的业务逻辑。`map`、`reduce` 没有消灭控制流，而是隐藏了遍历、累积等通用控制；`toUpper`、`sum` 等传入函数负责表达具体逻辑。目标是分离变化边界，不是追求函数式语法。
- what / how 相对于抽象层级存在：高层代码描述要完成哪些步骤，低层代码负责每一步如何完成；同一函数不要在组织主流程和展开协议、算法细节之间反复切换。
- 分层的意义是隔离变化、降低认知负担、支持协作，不是为了把目录凑齐。
- Request、DTO、ORM、外部协议对象不要直接进入核心业务层。

## 函数职责与抽象层级

- 函数只做函数名描述的那件事，内部语句保持同一抽象层级，不要一部分语句在描述整体步骤，另一部分语句又直接展开局部细节，否则阅读时会不断切换视角，增加理解成本。比如高层函数负责组织步骤，低层函数负责展开细节，高层函数写“做哪几步”，低层函数写“这一步具体怎么做”， 不要在同一个函数里来回切换“流程层”和“实现层”。
- 不同业务流程不要平铺在同一函数中
- 参数尽量少；布尔参数、行为枚举参数通常意味着函数职责混杂
- 函数应尽量遵循 Command-Query Separation：要么改变状态（有副作用），要么回答问题（无副作用），不要同时兼做
- 长度只作为复核信号，优先服从项目约定；核心判断是读者是否需要同时持有多个职责和抽象层级。
- 单文件接近或超过约 800–1000 行且混合多个流程、后端或生命周期时，将 review 升到
  [架构层](review.md#升级为架构-review-的信号)；不要用抽取无语义 helper 的方式降低行数。
- 参数超过调用者能一眼理解的范围时，考虑提取有语义的上下文对象，不要只为缩短签名制造 DTO。
- 上下文对象只聚合同生命周期、同变化方向的参数，并可承载与其语义相关的行为。

## 正确性与契约

- 先核对代码实际行为与需求、接口和测试声明是否一致，不从实现反推需求。
- 检查空值、边界输入、状态转换、失败清理和重试是否保持既定不变量。
- 区分真实缺陷与个人写法偏好；只有能说明错误结果、维护风险或契约破坏时才形成 finding。
