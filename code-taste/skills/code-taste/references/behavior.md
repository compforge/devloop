# 行为：控制流、职责与契约

## 控制与逻辑：分离关注点

- 程序 = Logic + Control。Logic 表达业务判断与变换，Control 决定执行顺序、分支、并发或重试方式；
  分离两者的变化原因，避免业务规则与协议适配、线程异步和调度胶水混在一起。
- 好的抽象固化稳定、重复的控制骨架，暴露持续变化的业务逻辑。例如 `map` 隐藏遍历，传入函数表达
  具体变换；判断收益看是否隔离变化，而非是否采用函数式语法。层间职责见 [模块化](modularity.md)。

## 函数职责与抽象层级

- 函数只做名字描述的事，内部语句保持同一抽象层级：高层组织步骤，低层展开实现，避免在主流程中
  穿插协议或算法细节；不同业务流程不要平铺在同一函数中。
- 用卫语句提前处理不满足前提的情况，让主流程保持平直；分支顺序服从依赖和业务语义。
- 参数只保留完成职责所需的信息；布尔参数、行为枚举或过宽上下文是职责混杂的复核信号。需引入
  上下文对象时，只聚合同生命周期、同变化方向的参数，不为缩短签名制造 DTO。
- 函数应尽量遵循 Command-Query Separation：改变状态与回答问题分别组织。
- 长度只是复核信号；难以单独理解时，按 [架构复核信号](review.md#升级为架构-review-的信号) 判断
  是否混合了职责，不用无语义 helper 缩短文件。

## 正确性与契约

- 从需求和接口声明核对行为，不从实现反推需求。检查主路径、边界输入、状态转换、并发、重试与
  失败清理是否保持不变量；公共参数校验由实现侧统一承接，调用方特有的业务判断仍由调用方负责。
- 新增或替换实现须保持调用方依赖的前置条件、完成条件、错误、副作用和一致性保证。例如“成功”
  表示已持久化时，不能悄悄改成仅入队；方法签名相同不等于行为可替换。
- 通过稳定的行为入口验证结果和不变量，业务规则与 I/O、框架胶水分开测试；仅在顺序属于契约时
  断言调用顺序。多个实现承诺同一行为时复用契约用例，真实适配器的事务、并发和故障语义仍需集成验证。
