# 命名原则

## 命名目标

名字是代码中的压缩语义，也是提供给人和 LLM 的局部提示。它会在声明、调用、搜索和上下文中反复出现；准确而稳定的名字让读者无需展开实现，就能激活正确概念。研究也表明，只替换标识符而不改变程序语义，仍会显著改变 Code LLM 的理解结果，误导性名字尤其容易把模型带偏
（[Wang et al.](https://arxiv.org/abs/2307.12488)、[Le et al.](https://arxiv.org/abs/2510.03178)）。

- 让人在使用点直接理解“它是什么”或“它做什么”，必要时体现 owner、阶段、规则或状态
- 优化每个词的语义密度，而不是单纯追求长或短；好名字增加少量 token，却减少反复展开实现的上下文
- 名字如果还需要额外解释，通常说明模型、职责或边界还没想清楚

## 优先顺序

- 准确，不制造错误预期；误导性名字比 `x`、`tmp` 这类无意义名字更危险
- 一致，同一概念使用同一个规范词，同一个词不承担多种含义
- 在使用点清楚；结合包、类型、函数和参数形成的完整表达判断，不孤立评价声明
- 先找业务概念，再表达意图，最后才考虑实现；清晰后再删掉重复语境和无效词

## 好命名特征

- 体现业务语义，例如动作、规则、状态、阶段和角色
- 能区分相近概念，而不是把不同东西都叫 `data`、`task` 或 `runtime`
- 与抽象层级一致；高层名字不泄露底层实现，底层名字不冒充领域概念
- 说清事实属于谁、描述哪个阶段或承担什么职责
- 采用团队和业界已有的规范词；除非是公认术语，不自造缩写、同义词或隐喻
- 函数名和类型名能把实现细节压缩成可复用概念，让调用方和 agent 不必先读函数体再继续推理

## 概念名内外有别

名字是否充分要结合模块边界判断。目录、包和类型已经提供稳定语境时，内部概念可直接使用 `Session`、`Controller` 等短名，不必把产品名和领域名重复塞进每个符号；例如 `http.Server` 优于`http.HTTPServer`。

概念跨出原有边界后，再由公共导出名或调用方的 import alias 补足语境。短名成立的前提是模块边界清晰，且同一作用域没有竞争语义；若调用方必须打开实现才能知道 `Session` 属于谁，应在边界处增加真正有区分度的限定词，而不是要求所有内部实现一起加前缀。

## 坏命名信号

- 名字暗示的 owner、行为、单位、状态或生命周期与实现不符
- `data`、`obj`、`temp`、`process`、`handle`、`manage` 等词单独承担核心语义
- `runtime` 只说明生效阶段，没有说明运行的对象和职责；只有它已是边界清晰的领域概念时才保留
- `info` 没有说明事实是 `State`、`Status`、`Result`、`Config`、`Capabilities` 还是 `Descriptor`
- `projector` 只说明“把输入映射成另一种表示”，没有说明产物、规则或业务意图；只有 projection 已是边界清晰的领域术语时才保留
- `xxxMap`、`xxxSet`、`xxxList` 等实现结构出现在业务边界
- 同一概念在 `Task`、`Job`、`Run`、`Execution` 等近义词之间漂移，或同一个词在不同地方含义不一致
- 只能靠注释解释真实含义；解释 `Mark` 的第一句总是“Mark 就是 finding”，应直接叫 `Finding`

## 命名纠结时

命名困难通常不是词汇量问题，而是当前解决的问题、对象边界或与相邻概念的差异还没有说清。按以下
顺序收敛：

1. 用一句话说明正在解决何种问题，并写出对象的 owner、生命周期、输入输出、关键不变量及与近邻概念
   的区别。
2. 选择名字必须承载的概念，再为每个概念选择团队已有的规范词；先搜当前仓库的模型、API、协议和
   调用点，避免为同一事物再造词。
3. 将问题句翻译成英文需求和领域术语，用 Web 搜索和 GitHub Code Search 查找实现同类需求的成熟项目。
   搜索“问题 + 角色 / 阶段 / 协议”，而不是只搜某个候选词或“naming best practice”；例如搜
   `sandbox snapshot restore`，而不是 `restore manager name`。
4. 阅读同类实现的核心模型、公开 API、状态枚举、错误名及调用点，观察一组词如何共同表达边界；README
   的营销用语和单个符号的词频只能提供命名灵感，不能作为结论。
5. 比较 2–3 个边界相近的实现，记录每个候选词包含和排除的语义。优先采用已有行业术语；若对象边界
   不同，增加真正有区分度的 owner、阶段或规则词，不机械照抄。
6. 把候选名放回真实调用处朗读，并用相邻 case 和反例验证。若每个名字都别扭，回到第一步调整模型或
   抽象边界，不用更长的名字掩盖问题。

局部临时变量能直接表达意图时，不必进行一轮行业调研；这套流程用于领域对象、状态、接口和会进入多处上下文的核心概念。

## 用类比生成候选词

类比可以显化抽象角色和关系，但只用于辅助建模和生成候选词。先把真实对象、owner、生命周期和关系逐项映射到类比，再提取词汇；翻译回领域词更清楚时，最终代码使用领域词。

若相邻需求需要不断制造牵强角色，立即放弃类比。同一领域不要混用多套隐喻；只有团队无需反复解释，且类比能稳定覆盖主要变化方向时，才让隐喻进入公开命名。

## 自检问题

- 这个名字描述业务意图，还是描述当前实现手段
- 只看声明和调用点，人或 LLM 会对 owner、动作、阶段、单位产生正确预期吗
- 同一概念是否在仓库中使用同一个词；这个词是否又被用于另一种概念
- 去掉 `runtime`、`info`、`context`、`manager`、`projector` 等泛词后，还剩下什么真实语义
- 如果实现从 map 换成 DB、从 HTTP 换成 RPC，这个名字还成立吗
- 完整使用表达是否清楚，还是重复语境，例如 `http.HTTPServer`
- 同类开源项目如何命名这个问题；它们的对象边界是否与当前一致
- 如果名字来自类比，新增相邻 case 时映射是否仍自然
