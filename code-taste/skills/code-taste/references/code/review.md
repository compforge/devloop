# 代码 Review

代码 review 判断实现是否正确、清楚且可维护地表达既定模型和行为契约。T1 直接使用本文件；T2 先完成
[[../architecture/review|架构 Review]]，再检查实现。若问题必须调整核心模型、模块 owner 或依赖方向才能
解决，将它升级为架构 finding，不在局部代码里打补丁掩盖。

## Review 顺序

1. 检查行为契约、边界条件和失败路径是否正确。
2. 检查命名、控制流和抽象层级是否让读者能直接理解意图。
3. 检查函数职责、局部依赖、封装与复用是否控制住复杂度。
4. 检查错误、日志和测试能否还原并约束真实行为。

findings first，按严重度或破坏性排序。每条 finding 指向具体代码和可触发场景，说明当前行为与预期
契约的差异；没有 finding 时明确说明，不用偏好性建议填充结果。

## 正确性与契约

- 先核对代码实际行为与需求、接口和测试声明是否一致，不从实现反推需求。
- 检查空值、边界输入、状态转换、失败清理和重试是否保持既定不变量。
- 区分真实缺陷与个人写法偏好；只有能说明错误结果、维护风险或契约破坏时才形成 finding。

## 先看可读性和模型，再看技巧

- review 先判断代码是否容易理解、是否体现业务模型、是否控制了复杂度
- 不要先被语法技巧、框架写法、性能小优化带偏
- 阅读者体验优先于编写者体验和机器体验

## 命名即设计

- 名字必须描述意图，而不是暴露实现细节
- 好名字的标准是：拿着代码给人讲时，不需要额外解释
- 技术名词频繁出现在业务代码里，通常意味着缺少业务模型

## 注释解释 why，不复述 how

- 注释优先解释为什么要这样设计、这样约束，帮助后来者理解决策背景和不能轻易改动的原因
- 少写或不写代码表面上已经能看出来的实现步骤，因为 `how` 往往更易随重构和实现调整而过时

## 函数要短小且单一

- 函数只做函数名描述的那件事，内部语句保持同一抽象层级，不要一部分语句在描述整体步骤，另一部分语句又直接展开局部细节，否则阅读时会不断切换视角，增加理解成本。比如高层函数负责组织步骤，低层函数负责展开细节，高层函数写“做哪几步”，低层函数写“这一步具体怎么做”， 不要在同一个函数里来回切换“流程层”和“实现层”。
- 不同业务流程不要平铺在同一函数中
- 参数尽量少；布尔参数、行为枚举参数通常意味着函数职责混杂
- 函数应尽量遵循 Command-Query Separation：要么改变状态（有副作用），要么回答问题（无副作用），不要同时兼做
- 长度只作为复核信号，优先服从项目约定；核心判断是读者是否需要同时持有多个职责和抽象层级。
- 单文件接近或超过约 800–1000 行且混合多个流程、后端或生命周期时，将 review 升到
  [[../architecture/review#升级为架构 Review 的信号|架构层]]；不要用抽取无语义 helper 的方式降低行数。
- 参数超过调用者能一眼理解的范围时，考虑提取有语义的上下文对象，不要只为缩短签名制造 DTO。
- 上下文对象只聚合同生命周期、同变化方向的参数，并可承载与其语义相关的行为。

## 先消除耦合，再谈复用

- 业务逻辑和控制逻辑混在一起，是最常见的复杂度来源
- Request/DTO/ORM 穿层传递，会让边界和依赖失稳
- 遇到重复时，先判断是不是同一概念，再决定是否抽取共享方法
- 守卫逻辑（参数有效性检查、空值处理）应放在实现侧统一处理，不在调用侧重复

## 封装要提供行为，不要只搬运数据

- 对象应暴露有语义的行为，而不是一串 getter/setter
- 避免火车残骸式调用链，让对象自己完成与自身语义相关的事
- 对价格、ID、状态等有业务含义的值，优先考虑值对象封装

## 日志和错误必须能还原现场

- 日志和错误必须说明：在做什么、哪个对象/参数出问题、关键值是什么
- 只写“failed”“invalid param”这类信息，等于把排障线索主动抹掉
- 返回 error、异常、错误码都可以，但问题必须透明

## 格式服务于理解

- 用空行切分语义块，不要把多段逻辑压成一坨
- 高概率分支优先返回，减少无谓嵌套
- `if-return` 的卫语句通常比冗长的 `if-else` 更易读

## 检查清单

### 正确性与测试

- 主路径、边界输入、失败路径和清理逻辑是否符合行为契约？
- 状态转换、并发、重试或超时是否会破坏不变量？
- 测试是否覆盖本次真正改变的行为，而不是只执行了代码？

### 命名

- 类、函数、变量名是否直接表达意图？
- 是否充斥 `data`、`info`、`manager`、`processor`、`handler` 等宽泛词？
- 是否使用 `xxxMap`、`xxxSet` 等实现导向命名掩盖业务概念缺失？

### 函数与抽象层级

- 函数是否只做一件事，内部语句是否处于同一抽象层级？
- 是否通过布尔参数、行为枚举或过宽上下文切换多种职责？
- 是否存在明显可以提前返回却仍然嵌套很深的结构？

### 模块与依赖

- 业务逻辑是否和流程控制、协议适配、存储细节混在一起？
- 是否有 Request、DTO、ORM 或外部协议对象穿透层级？
- 依赖是否朝稳定抽象流动；若不成立，是否应升级为架构 finding？

### 抽象、复用与封装

- 重复代码是否真的是同一概念？
- 抽取后的共享方法是否语义清晰，比明确重复更容易维护？
- 对象是否提供有业务语义的行为，而不是暴露数据让调用方拼装？
- 是否出现大量 getter/setter 或火车残骸式调用链？

### 日志、错误与可读性

- 日志是否带操作名、对象标识、关键参数和值？
- 是否吞错、静默忽略失败或只返回模糊错误码？
- 不同语义块是否清楚，高概率路径是否优先返回？
- 是否存在过长链式调用、炫技式函数式写法或难读嵌套？
