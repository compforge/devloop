# 文档分层与写作原则

文档不是代码事实的副本。先判断信息的读者、稳定性和获取成本，再决定写在哪里；越稳定、越需要跨
文件或跨决策才能理解的信息越往上放，越易变、越容易从代码直接读出的事实越往下放。

## 分层模型

| 层级 | 主要读者 | 适合承载 | 不应承载 |
|---|---|---|---|
| `AGENTS.md` | 初次进入项目的人和 agent | 项目定位、代码地图、长期边界、关键约定、References 索引 | 流程展开、字段参数、阈值、例外分支 |
| `docs/<feature>.md` | 关心某项能力或设计的人 | 理念、概念、主流程和关键设计的 why，可点名少量模块作锚点 | 跟着代码频繁变化的实现形状 |
| 意图标记（如 `spec` / `case` / `rule` / `link`） | 修改代码并追溯其依据的人和 agent | 贴近代码的意图、规范、约束，以及到相关资产的可寻址关系 | 长篇原理、没有稳定目标的自由文本、只靠标记保证的高代价约束 |
| 代码注释 / docstring | 修改或调用局部代码的人 | 隐式约束、顺序依赖、调用契约、易错场景 | 对代码表面行为的复述 |
| 代码 | 所有实现读者 | 字段、参数、阈值、分支和当前实现 | 需要跨文件或跨决策才能恢复的设计意图 |

## 意图标记连接代码与文档

意图标记可以理解为**绑定到代码 symbol 的结构化注释**，更准确地说，是结构化意图注释。它保存
那些无法仅从实现稳定还原、但修改代码时必须理解的诉求；与代码共置，同时比自由文本注释更有类型、
更容易搜索、追溯和机检。它何时值得存在、应绑定哪个 symbol，以及 `spec` / `case` / `rule` / `link`
如何分工，详见 [[mark|结构化意图标记]]。

## README 面向使用者

- 先说明产品或项目是什么、解决什么问题、具备哪些核心能力。
- 简要解释主要概念和领域对象，再用短小的数据流或控制流串起它们。
- 保留安装、必要配置和最短使用路径。
- 把生命周期、内部边界、设计取舍和实现细节下沉到设计文档或代码。
- 不把 README 写成目录清单、接口参考或实现说明书。

## AGENTS.md 保持高密度

- 围绕 `项目定位与边界`、`代码地图与核心模块`、`关键约定`、`References` 组织；已有文件优先渐进式收敛，不为格式统一而整体重写。
- 代码地图默认使用 tree 风格代码块表达目录层级，并在目录或关键文件行尾写明职责和所有权；路径只
  作为定位锚点，不代替能力描述。只有不强调层级、确实需要横向比较多个属性时才使用表格。
- 把关键约定控制在少量长期稳定、跨实现且不能破坏的模型、边界或依赖；合并同源规则。
- 每个设计点用一两句话说清“有这件事、为什么有”，详细说明通过 References 下沉。
- 使用仓库内相对路径；命令中的仓库根目录使用 `<repo_root>` 等占位符，避免写入个人机器路径。

## 设计文档解释 why

优先采用三段式：

1. **理念 / 概念**：定义核心词汇、对象语义和它们之间的关系。
2. **流程**：从触发点到结果描述主链路，只点名帮助定位的关键模块。
3. **关键设计**：每节回答一个“为什么这样做”，说明边界和主要取舍。

描述当前系统成立的模型，默认以绿地视角直接写最终状态：说明现行概念、协议、owner 和边界，不按
实现时间写“第一阶段 / 第二阶段 / 后续”，也不写“旧字段已删除 / 不再兼容 / 从 A 迁到 B”这类
迁移叙事。只有历史背景仍会约束当前决策时才保留，并压缩成“现行约束 + 原因”；迁移步骤和版本差异
放在变更单、MR 或发布计划，不进入长期设计文档。不要把字段路径、固定阈值和 case-by-case 分支搬进
设计文档。

### 可选的 `docs/kernel.md`

当多个功能共享一套稳定的核心分层、执行模型和扩展边界时，可以用 `docs/kernel.md` 描述项目内核：

- 内核负责什么、不负责什么，以及它与业务扩展或外部适配的边界。
- 核心模块的分层、依赖方向和主要生命周期。
- 跨功能复用的控制流、数据流、扩展点和信任边界。

由 `AGENTS.md` 简要说明内核存在并链接到它，各 feature 文档只描述自己的领域差异。若项目没有独立、
稳定且被多个功能共享的内核模型，就不要为了文档目录完整而创建 `kernel.md`；也不要把它写成源码目录
索引或所有功能文档的合集。

## 注释区分维护者与调用者

- 在函数内部用行注释解释 why、非显而易见的顺序依赖和容易被误改的约束。
- 在类或公开方法的 docstring 中说明调用契约、参数语义、使用约束和易错场景，让调用方无需打开实现即可正确使用。
- 不复述函数名、类型和语句已经表达的 how；实现演化史不堆进 docstring。

## 落笔前自检

1. 代码一改，这段文字是否必须同步？若是，优先放进注释或代码。
2. 只看代码能否直接拼出这条信息？若能，不放进 `AGENTS.md` 或设计文档。
3. 是否必须跨多个文件或多次决策才能理解？若是，才值得进入高层文档。
4. 这条内容是在解释能力和边界，还是只罗列目录、字段和参数？后者下沉。
5. 文档是否便于扫描？
   - 一个段落只表达一个中心意思；出现多个并列判断、步骤或例外时，拆成列表或小节。
   - 同层列表项保持相近粒度；某一项明显更复杂时，保留该项作为主题，再用二级列表展开。
   - 用嵌套表达真实层级，但不为追求“短”把每句话都切成孤立 bullet。
6. 文档组织是否仍反映当前核心概念、流程和 owner，而不是按需求到达顺序持续堆叠？批量需求后的整理见
   [[/references/architecture/evolution#MR 序列复盘|MR 序列复盘]]。
7. 文档是否已经过长？单文件接近 300 行时先删重复、细节和迁移叙事，再考虑拆分。
8. 删除“旧 / 新 / 阶段 / 后续 / 兼容”这类时间标签后，文档能否仍以现行模型自洽？若不能，先把
   稳态契约写完整，再决定是否确有必要保留历史原因。
