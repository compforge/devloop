# 演进：绿地审视与增量调整

绿地视角用于检验业务模型、服务协作和应用内部组织，增量演进负责将必要调整落实到当前系统。它连接 [业务建模](modeling.md) 与 [职责和边界](modularity.md)，帮助判断保留什么、调整什么，以及调整到什么程度。

## 从问题到调整

**“你观察到了什么，因此选择了什么，放弃了什么”**

按问题影响选择深度；局部缺口只展开相关概念、流程与职责：

1. 还原原始需求和非功能性约束，包括性能、扩展性、可维护性、团队能力与发布时间，不把当前实现当成问题定义。
2. 识别当前仍然成立的设计：核心概念、关系、主流程、查询键与生命周期，以及承担它们的服务、模块、契约和依赖。判断复杂度原本靠哪些机制控制。
3. 用下面的绿地视角检查模型与分工是否足以承接需求。比较主要备选时，说明哪些领域规律、变化模式或实际限制导出了选择，区分已知事实与待验证假设，并指出什么证据会改变方案；有真实长期场景时用其检验边界。
4. 对照现状安排必要调整：明确哪些概念与规则保留、哪些契约或能力补齐，以及由哪些层共同完成。再检查接口、复用与具体实现。

**“复杂度不会凭空消失。”** 比较方案的复杂度时，说明哪些被消除，哪些被封装、转移或推迟，以及
最终由谁承担；同时计算调用方、实现方与运维的成本，不能只以当前模块变短判断收益。

技术选择尚不确定时，尽早验证正确性、容量和恢复能力的关键假设；实现选择是否推迟，取决于当前
隔离成本、以后迁移成本和等待能获得的信息。例如数据库产品可以晚选，原子更新与一致性要求仍需
先明确。局部封装足以保留选择时，不预建通用框架；证据已充分或延迟妨碍交付时，应作出决定。

## 绿地视角

暂时放下现有服务划分、方法、类和调用关系的限制，假想今天从零设计、把当前需求当作一等公民。按问题涉及的范围审视：

- **业务架构上**：需要哪些概念、关系和主流程？现有模型是自然容纳新 case，还是缺少身份、归属、生命周期或必要协作？
- **系统架构上**：职责与权威数据应由哪个服务拥有？调用、消息、一致性与恢复责任是否匹配这些边界？
- **应用架构上**：既定职责如何落实到模块和接口？哪一层的能力或 contract 不足，哪些逻辑放错了位置？

三个视角可以得到不同结论。业务模型与服务 ownership 都正确时，宽查询问题可以集中修正 Repository 的数据契约与 DAO 的查询能力；多个服务争相转换同一状态时，要先明确跨服务的权威来源与协调契约；反复新增业务特判时，则可能要先收束概念，再确定实现落点。应用内部存在缺口，并不意味着要拆分服务。对应案例见 [宽查询的数据契约](examples/query-scope-follows-consumer.md) 和 [新增维度的模型调整](examples/scope-not-special-case.md)。

- 做法显而易见且符合契约时，通常可以沿既有主路径实现；做法不再自然时，先检查设计缺口，不利用代码缝隙继续加分支。
- 新增维度影响资源归属、查询键、生命周期、复用或回收策略时，先检验 [模型是否充分](modeling.md#什么值得进入模型)。
- 找到最小充分模型和分工，再比较现状差距：差距小就局部补齐；差距涉及模型或边界，就围绕该缺口调整相关协作。
- 绿地视角校准收敛方向；落地仍尊重实际约束并增量演进，不预建无当前需求的对象、层级或协议。

## 长期方向

- 用有需求或历史证据的长期场景检验当前设计：会新增哪些参与者、生命周期与恢复边界，需要修改
  哪些模块、契约、测试和发布单元？区分必要协作与内部细节泄漏造成的联动。
- 比如新增执行后端时，既检查接口，也检查准备、执行、错误解释和资源清理是否仍须分散增加分支。
- 场景用于校准边界，落地按当前阶段做最小闭环，不提前实现终局。

## MR 序列复盘

- 单个 MR 天然是一个具体问题的局部解；概念缺口往往只有把近期 merged MR 串起来才会显形。
- 演进视角不要求每做一个需求就重构全局。先完成当前最小闭环；同一主题积累约三个补丁后，再回看
  它们是否在反复修同一个缺失概念或流程的不同变体。
- 复盘先判断模型处于哪种状态：
  - **开始成型**：多个需求反复出现相同身份、owner、生命周期、流程阶段或判断入口，应收束为显式模型。
  - **仍然成立**：现有核心概念和流程可以自然容纳新增需求，应继续保持，不因改动数量多而强行重构。
  - **仍在探索**：case 之间只有表面相似，语义和变化方向尚未稳定，应保持松散，避免过早抽象。
- 模型判断之后，同步检查表达它的组织是否已经落后：
  - **服务协作**：职责、数据 ownership、通信与恢复责任是否仍匹配业务流程，还是随补丁逐渐形成隐式跨服务约定。
  - **代码组织**：目录、模块、接口和依赖方向是否仍围绕真实 owner 与流程，还是按历次需求不断旁挂分支。
  - **文档组织**：术语、代码地图、feature 文档和 References 是否反映当前模型，还是按需求到达顺序堆叠。
  - **保持也是结论**：若模型和组织仍匹配，不为了“做过复盘”制造无收益的重排。
- 识别出的缺口按强度落地：
  - **显式概念**：命名并写进术语文档；
  - **类型**：把裸 string、约定式 dict 等隐形协议变成显式类型；
  - **结构**：升级为文件、目录与模块边界；
  - **单一判断入口**：把同主题判断收成 policy 函数或模块。
- MR 序列指出“哪里反复疼”，绿地视角回答“该往什么形状收敛”，二者构成自底向上的设计循环。
- 功能逐项可用不代表组合后的模型仍然清晰。架构显性化应让维护者不必先理解全仓，就能预测新需求的
  改动落点、协作流程与必须守住的约束；用近期几个真实需求反查这些落点，验证设计是否减少了理解
  成本与改动扩散，而不只增加了名字、目录和接口。

## 约束机制化

利用领域规律限制允许的状态与行为，可以缩小问题范围、简化设计。说明约束带来的收益、排除的需求、
负责保证它的 owner，以及约束不再成立时如何调整，再选择承接机制。

- 多人并行项目里，什么都不发生的文档约束等于不存在；每个 MR 都只看局部，不能依赖所有人先读完
  全部设计说明。
- 散落变体积累到一定程度，就给约束一个代码形状：Protocol / 接口、outcome 类型、模板方法或
  单一入口。此后绕开设计会在类型检查或 diff 中显形。
- 执行力按违反代价逐级提高：
  1. **文档宣告**：只说明有这件事，最弱；
  2. **结构显性化**：显式抽象收编多个实现，或单一入口收回流程所有权；
  3. **可执行契约**：参数化测试枚举所有路径，违反即 CI 失败；
  4. **运行时对账**：跨存储一致性等测试锁不完的问题，由 reconciler 自愈并留下日志 / metric。
- 违反只伤可读性，文档与命名足够；会造成状态不一致或任务卡死，至少需要结构 + 契约测试；
  横跨多个存储面时再增加运行时对账。
- review 中若发现“文档宣告唯一入口，旁边却已长出新变体”，就是约束需要升级的信号。

反面案例见 [约束靠机制守住](examples/constraint-by-mechanism-not-docs.md)。
