# 守卫逻辑放在实现侧，不在调用侧

- 背景：`mark_message_error` 和 `mark_message_finished` 接受 `message_id` 参数，但 `message_id` 可能为 `None`
- 反例：在每个调用侧都加 `if message_id:` 守卫
  - 问题在于守卫逻辑重复散落在多个调用点
  - 每次新增调用点都要记得加守卫，容易遗漏
  - 调用侧关注的是业务流程，不应被参数有效性检查打断
- 正例：在 repo 实现侧统一处理
  - 接口签名改为 `message_id: str | None`
  - 实现开头统一 `if not message_id: return`
  - 调用侧直接传参，不需要任何守卫逻辑
- 关键判断：守卫逻辑属于实现细节，应该由实现方统一处理，而不是让每个调用方都重复检查
- 适用边界：
  - 适用于参数有效性检查、空值处理、前置条件验证等防御性逻辑
  - 适用于多处调用同一方法的场景
  - 不适用于业务规则判断（业务规则应该显式化，不应隐藏在实现内部）
