# 用状态转换明确生命周期规则

## 背景

订单逐步增加支付、履约和退款能力，各入口开始依赖多个状态字段决定能否操作。
本例以需要审核的全额退款为示意，说明如何细化业务模型；不代表具体项目的已验证实现。

## 反例

申请接口、审核任务和支付回调分别判断、修改 `is_paid`、`is_refunding`、`is_refunded`。
“退款完成后不能再次执行退款”等规则散落在各处，新增路径容易漏掉某个条件或字段更新。
即使把这些判断搬进名为 `RefundService` 的类，若各方法仍自行组合条件，合法状态与转换规则依然不清楚。

## 正例

先明确支付、履约与退款各自的生命周期和 owner。支付成功可以成为申请退款的条件；退款完成后，
支付成功的历史事实仍然成立，履约如何停止或回收则由相应业务契约规定。

退款 owner 维护退款对象的状态与行为入口。下面列出部分转换，展示应明确的规则：

| 当前状态 | 事件与条件 | 转换及动作 |
|---|---|---|
| 待审核 | 审核通过，满足退款资格与金额约束 | 进入处理中，安排退款执行 |
| 待审核 | 审核拒绝 | 进入已拒绝，记录原因 |
| 处理中 | 收到并核验该退款的成功结果 | 进入已完成，记录结果 |
| 已完成 | 再次收到同一成功结果 | 保持已完成，幂等返回，不重复执行副作用 |

对未允许的操作明确拒绝语义；对重复事件明确幂等语义。超时、失败与重试按实际业务补齐，
外部请求被接受时仍处于处理中，只有确认结果后才能进入已完成。

## 关键判断

- **业务模型**定义状态、事件、转换条件与不变量。先决定什么变化合法，再安排各条路径的执行步骤。
- **应用内分工**让退款对象或 Biz 维护转换规则，Service 组织加载、调用与结果协调；简单场景可由同一业务组件承担。
- **执行保证**需要结合并发与外部协作落实：例如用版本条件更新防止基于旧状态的写入，并明确外部退款与本地记录之间的幂等和恢复责任。状态图本身不能保证这些动作一致完成。

## 适用边界

适用于行为受生命周期阶段约束、合法转换本身构成重要业务规则的概念。仅有可变字段时无需引入状态机；
相对独立的生命周期分别表达，避免把支付、履约、退款的所有组合摊成一个巨大的状态枚举。
简单转换可由枚举与业务方法表达，转换表或状态机库按复杂度选用。验证应覆盖允许与拒绝的转换、
重复事件及关键不变量；涉及并发或外部副作用时，再验证相应的一致性与恢复契约。
