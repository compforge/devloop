# 从宽查询追到消费方数据契约

## 背景

一个慢 SQL 问题来自范围过大的共享 DAO 查询：多个 Service / Biz 组件读取同一集合，再各自过滤掉不需要的数据。以下方法名为示意，案例用于说明改动如何分派，不代表已验证的具体仓库实现。

## 反例

多个组件调用 `ListByRuntime(runtime)`，再各自按状态过滤。修复只给 SQL 加索引或将全量读取改成分页，调用方仍读取全部历史对象。查询成本可能下降，但共享方法仍把过宽的数据契约强加给不同消费者。

## 正例

先明确每个业务组件需要哪些对象：例如 Observer 需要继续观测的候选对象，由业务 owner 定义相应状态范围。已有 Repository 时，`ListObservationCandidates` 表达这一数据需求；DAO 通过 `ListByRuntimeAndStatuses(runtime, statuses)` 等查询能力在数据库筛选。没有 Repository 且访问简单时，组件直接调用适当的 DAO 查询即可。

Repository 仍可隐藏分页与批量加载细节，业务组件对候选对象执行动态判断。查询条件收窄后，再根据实际查询检查索引等执行效率。

## 关键判断

- 业务上先判断是否缺少概念或流程；若对象范围已清楚，问题可能是数据契约没有表达需求，无需额外引入业务概念。
- 实现上按职责安排消费方、Repository 与 DAO 的协作，修复落点由责任决定，不由慢 SQL 所在文件决定。
- 共享查询机制不等于共享数据范围；业务规则由 Biz 决定，也可以通过明确条件在数据库执行。

## 适用边界

适用于不同消费者读取宽集合后重复丢弃数据的情况。完整对账等业务可能确实需要全量遍历；依赖外部实时状态或动态策略的判断，也可能需要在取得候选集后执行。收窄查询须保持所需结果完整，不用任意 LIMIT 掩盖范围问题，也不为简单访问额外建立 Repository 或通用查询框架。
