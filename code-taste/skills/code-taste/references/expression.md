# 表达：命名、文档、注释与日志

表达是把脑中的问题模型转换成别人和机器能够理解、使用和检查的共享模型。代码、接口、类型、
测试和文档共同承担这件事。先确定读者需要理解什么、作出什么判断或行动，再选择载体、抽象层次
和必要细节。术语准确是基础；详略得当体现对模型的掌握。

读者包括使用者、开发者、评审者、其他协作人员，以及执行 vibe-coding 的 AI。按当前任务决定
他们需要的上下文，不按身份预设理解深度。像 code-taste 这样的 skill 文档本身也是协作约定：
既要让 AI 理解适用条件并据此行动，也要让协作者检查判断依据，关键规则不依赖先前对话才能成立。

表达是否充分，要看读者能否据此解释当前行为、识别成立条件，并对相邻的新场景作出正确判断。
用实践中的变体检验模型，不靠复述术语或熟悉的案例证明理解；提升抽象层次应帮助解释问题和作出
决策。具体行为仍需由实现、测试或运行证据验证。

## 命名

### 判断标准

名字是代码中的压缩语义，让读者在使用点理解对象是什么、操作做什么，以及必要的职责、阶段或
状态。命名困难时，先检查概念与边界是否清楚。

- **准确**：名称与实际语义、生命周期、单位和副作用相符。
- **一致**：同一概念使用同一个规范词，不让一个词承担不同含义；优先复用项目已有领域词汇。
- **符合层级**：高层名称表达业务意图；实现机制在它所属的层次命名。
- **上下文充分**：结合包、类型和调用点判断信息是否完整，再删去重复语境与无效词。

目录、包和类型已经提供稳定语境时，内部概念可以用 `Session`、`Controller` 等短名，例如
`http.Server`。跨模块或公共边界后，由导出名或 import alias 补足职责，避免调用者必须打开实现
才能辨别含义。

`data`、`info`、`manager`、`handler` 等泛词，以及 `xxxMap`、`xxxList` 等容器名，若独自承担业务
含义，应检查是否缺少更准确的概念；这些词在已有明确职责的语境中仍可使用。若名称只能靠注释
纠正含义，优先修正名称。

### 命名困难时

先用一句话说明问题，以及对象的职责、输入输出、生命周期和相邻概念的区别；再搜索仓库已有
模型与调用点，将候选名放回实际使用处检查是否自然。

仓库内证据不足、需要确认行业通用语义时，再用需求和领域词汇查找成熟实现。比较它们的模型、
公开接口与使用场景，确认边界一致后再借用名称，不以词频或 README 宣传语作为结论。普通局部
命名无需展开行业调研。

类比可以帮助发现候选概念，但要能说明对象、关系与约束的对应方式，并用新的实际场景检验。
若类比需要不断增加牵强解释，就回到领域本身的词汇。

## 文档与写作

### 内容归属

先按读者任务选择载体，再用稳定性和获取成本决定详略。实现细节靠近代码；使用契约与跨模块
设计应让相应读者直接找到。即使信息能从代码推导，只要读者完成任务需要它，就应在适当载体中
提供；可生成的接口细节优先由代码生成，避免重复手工维护。

| 载体 | 读者当前的任务 | 应形成的理解与能力 |
|---|---|---|
| `README.md` | 判断项目是否适用、开始使用或接入 | 理解问题、能力边界和使用方式，完成第一次有效使用 |
| `AGENTS.md` | 开发者或 AI 准备修改项目 | 恢复职责地图与关键约束，定位改动归属、依据和验证入口 |
| `docs/kernel.md`（可选） | 协作者理解系统整体、判断扩展归属 | 掌握最小充分的核心概念、关系、主流程和共同约定 |
| `docs/<feature>.md` | 理解某领域机制、评估设计或修改 | 根据问题、机制、取舍和成立条件，推理新场景及改动影响 |
| Blog | 从实践中学习、交流设计判断 | 跟随从具体问题到抽象模型的推理，将理解迁移到自己的场景 |
| 注释 / docstring / 意图标记 | 调用、修改或评审局部代码 | 掌握代码未充分表达的意图、约束和调用契约，并追溯设计依据 |

同一模型在不同载体中可以有面向任务的摘要；完整解释由一个明确位置维护，其他位置链接过去。
代码和测试分别承载可执行行为与验证；文档帮助人和 AI 理解其意义、边界和判断依据。

### 维护已有文档

维护时先找内容归属，阅读相关上下文，再改写已有表达，同时删除被新表达替代的重复或失效内容。
改动范围以相关主题为单位，可以重写一个段落或小节，使其完整表达当前模型。

- 新信息属于已有主题时，融入对应位置；能由已有定义自然推出的结论，不再逐条补充防误解说明。
- 新增章节应有独立的读者问题或内容职责；新增文件还应有清楚的维护归属与独立阅读价值。同一
  概念的使用指南和设计说明可以服务不同任务，无需为拆分强造新概念。
- 文档组织反映当前概念、流程和职责。用标题与链接检查主线，不按需求到达顺序保存讨论痕迹；
  多次相关改动后的复核见 [MR 序列复盘](evolution.md#mr-序列复盘)。
- 文档过长时，先删重复、过时内容和不属于该读者任务的细节，再判断是否需要拆分。行数只用于
  提醒复核，不决定文档是否合理。

以上用于获授权直接维护的文档。作者稿件的建议模式按下文 Blog 的协作改稿约定处理。

### README 面向使用者

README 帮助读者判断项目解决什么问题、输入与结果是什么、哪些约束决定是否适用。领域概念要
说明它向使用者提供什么、需要使用者提供什么；保留影响接入判断的技术细节。

通常需要回答定位与价值、核心能力、核心概念、快速开始四类问题，可按项目规模合并组织。
项目确实支持扩展或存在必要的深入材料时，再提供相应入口。短小的流程图应帮助预测使用行为；
详细实现和设计推理链接到开发文档。

### AGENTS.md 帮助定位与行动

AGENTS.md 面向准备动手的开发者和 AI，帮助他们判断改动属于谁、哪些边界必须保持、到哪里找
依据，以及如何验证。高密度意味着保留决定行动的信息，并解释必要的理由。

- 围绕项目定位与边界、代码地图与核心模块、关键约定、References 组织；按实际缺口逐步整理。
- 用简短的核心概念和主流程说明工作模型；跨服务场景交代职责、数据归属与通信边界，详细设计
  通过链接展开。
- 代码地图默认用 tree 表达层级，并在关键目录或文件后说明职责。横向比较属性时使用表格。
- 关键约定聚焦少量稳定的模型、边界和依赖；合并同源规则，每个设计点用一两句话说明存在及原因。
- 使用仓库内相对链接；命令里的仓库路径使用 `<repo_root>` 等占位符，避免绑定个人机器。

### 设计文档与概念地图

设计文档说明原始问题和约束如何导出当前模型，关键取舍解决了什么、付出了什么代价。通常按
“概念与关系 → 主流程 → 关键设计与理由”展开，从具体场景引入抽象，并说明成立条件。

默认以绿地视角描述现行模型、协议、职责和边界。历史原因只有仍约束当前判断时才保留，压缩为
现行约束及其理由；迁移步骤、版本差异和交付进度归入 MR、变更记录或发布计划。

围绕核心概念展开设计；内部对象、存储格式与 UI 投影放在其所属概念下。文档标题和链接应与
[代码与目录地图](modularity.md#代码与目录地图) 表达同一套职责。若必须读完很多平级名词才能
拼出主流程，先检查模型或内容归属。

`docs/<feature>.md` 解释该领域特有的问题、机制和取舍。关键协议语义、失败恢复约束等会影响
判断的细节应保留；跟随实现频繁变化的字段清单和分支细节，通过代码或接口参考定位。

### kernel.md 表达共享内核

当多个功能确实共享稳定的分层、执行模型和扩展边界时，可以用 `docs/kernel.md` 描述：
**最小充分模型 + 串联核心概念的主流程 + 关键约定**。

它说明内核职责、模块协作、主要生命周期，以及跨功能共用的扩展点和信任边界，让读者能判断
新增能力的归属。`AGENTS.md` 提供入口，各 feature 文档只展开自身差异。是否需要独立 kernel
文档取决于共享模型的阅读价值，而非目录完整性。

### Blog：表达思路与协作改稿

#### 组织思路

围绕一个读者问题形成主线：从真实场景和约束出发，解释如何建立模型、选择抽象和作出取舍，
让读者能将理解迁移到其他问题。介绍产品时，先说明用途和使用方式，再用必要的机制解释能力。

新术语随场景引入；已有文章以短摘要和链接承接。示例、伪代码和配图应帮助理解推理或结果，
注明示意与省略，保留作者表达习惯。素材缺失时留占位，不编造效果和证据。

#### 占位与修改标记

每轮先读取作者当前文件，以手动修改后的版本为准。已有稿件默认保留原文；未明确要求直接改写时，
补充与删改采用以下可审阅标记，便于作者逐项取舍：

- **补充**：用 Markdown 斜体 `*补充内容*` 标记新增文字，包括标题和过渡句；多段补充分段标记。
  代码块等不能整体呈现斜体的素材，在块外用 `*补充开始*`、`*补充结束*` 标明范围。
- **建议删除**：用 `~~建议删除的原文~~` 保留原句并标记删除线。建议替换写成
  `~~原文~~ *建议的新文字*`；代码块等不适合行内删除线的内容，在块外说明删除建议并保留原块。
- **素材占位**：使用引用块 `> TODO：补充什么素材，用来说明什么`，使待补项在预览中可见；
  引用块前后留空行，沿用作者署名格式，缺失链接也按此标注。
- **只重组**：用户要求移动文字但不改措辞时，整段移动并保留原句与代码，新增衔接用斜体。
  错字、术语或伪代码问题单独指出。
- **应用修改**：用户明确要求直接修改或接受某项建议后，在授权范围内应用，保留其他待定标记。
  要求“看下、理解、给建议”时先在回复中反馈。

示例：`~~平台能够处理所有业务。~~ *平台提供公共运行能力，业务通过扩展表达自己的流程。*`

## 注释与意图标记

函数内部的行注释说明局部隐式约束、非显而易见的顺序依赖和易错理由；类或公开方法的 docstring
说明调用契约、参数语义和使用限制，让调用方无需打开实现即可正确使用。

需要随稳定 symbol 保存、供静态分析提取及后续修改和评审使用的契约与设计理由，使用
[结构化意图标记](mark.md)。
标记的分类、挂载位置及验证关系统一在该文档维护。跨模块推理通过链接指向设计文档，局部说明
保留理解当前改动所需的上下文，不重复函数名和语句已清楚表达的行为。

## 日志和错误必须能还原现场

日志与错误面向判断运行状态、排查问题的人和 AI。记录关键动作、状态变化及异常分支，说明
正在做什么、涉及哪个对象、相关输入或状态以及失败原因。只写 `failed` 或 `invalid param`
不足以定位问题。

使用低噪声、带上下文且不含敏感信息的记录；稳定的设计理由留在代码旁，日志记录此次执行的
事实和决策依据。错误码支持程序判断，错误信息支持现场理解。

## 表达检查

- 读者能否据此作出预期判断或行动，并解释一个相邻的新场景？
- 抽象层次和细节是否服务当前任务；名称与正文是否准确表达同一个模型？
- 同一原则是否已有明确归属；本次修改是否留下重复、失效内容或对先前对话的依赖？
- 连贯段落是否讲清因果；列表是否承载真正并列的项或步骤，且粒度一致、层级清楚？
- 链接能否找到完整依据，示例与结论能否由实现或证据支持？

控制流和局部实现的可读性见 [行为](behavior.md)，模型与设计的评审见 [review](review.md)。
