# 表达：命名、文档、注释与日志

## 先看可读性和模型，再看技巧

- review 先判断代码是否容易理解、是否体现业务模型、是否控制了复杂度
- 不要先被语法技巧、框架写法、性能小优化带偏
- 阅读者体验优先于编写者体验和机器体验

## 命名

### 命名即设计

- 名字必须描述意图，而不是暴露实现细节
- 好名字的标准是：拿着代码给人讲时，不需要额外解释
- 技术名词频繁出现在业务代码里，通常意味着缺少业务模型

### 命名目标

名字是代码中的压缩语义，也是提供给人和 LLM 的局部提示。它会在声明、调用、搜索和上下文中反复出现；准确而稳定的名字让读者无需展开实现，就能激活正确概念。研究也表明，只替换标识符而不改变程序语义，仍会显著改变 Code LLM 的理解结果，误导性名字尤其容易把模型带偏
（[Wang et al.](https://arxiv.org/abs/2307.12488)、[Le et al.](https://arxiv.org/abs/2510.03178)）。

- 让人在使用点直接理解“它是什么”或“它做什么”，必要时体现 owner、阶段、规则或状态
- 优化每个词的语义密度，而不是单纯追求长或短；好名字增加少量 token，却减少反复展开实现的上下文
- 名字如果还需要额外解释，通常说明模型、职责或边界还没想清楚

### 优先顺序

- 准确，不制造错误预期；误导性名字比 `x`、`tmp` 这类无意义名字更危险
- 一致，同一概念使用同一个规范词，同一个词不承担多种含义
- 在使用点清楚；结合包、类型、函数和参数形成的完整表达判断，不孤立评价声明
- 先找业务概念，再表达意图，最后才考虑实现；清晰后再删掉重复语境和无效词

### 好命名特征

- 体现业务语义，例如动作、规则、状态、阶段和角色
- 能区分相近概念，而不是把不同东西都叫 `data`、`task` 或 `runtime`
- 与抽象层级一致；高层名字不泄露底层实现，底层名字不冒充领域概念
- 说清事实属于谁、描述哪个阶段或承担什么职责
- 采用团队和业界已有的规范词；除非是公认术语，不自造缩写、同义词或隐喻
- 函数名和类型名能把实现细节压缩成可复用概念，让调用方和 agent 不必先读函数体再继续推理

### 概念名内外有别

名字是否充分要结合模块边界判断。目录、包和类型已经提供稳定语境时，内部概念可直接使用 `Session`、`Controller` 等短名，不必把产品名和领域名重复塞进每个符号；例如 `http.Server` 优于`http.HTTPServer`。

概念跨出原有边界后，再由公共导出名或调用方的 import alias 补足语境。短名成立的前提是模块边界清晰，且同一作用域没有竞争语义；若调用方必须打开实现才能知道 `Session` 属于谁，应在边界处增加真正有区分度的限定词，而不是要求所有内部实现一起加前缀。

### 坏命名信号

- 名字暗示的 owner、行为、单位、状态或生命周期与实现不符
- `data`、`obj`、`temp`、`process`、`handle`、`manage` 等词单独承担核心语义
- `runtime` 只说明生效阶段，没有说明运行的对象和职责；只有它已是边界清晰的领域概念时才保留
- `info` 没有说明事实是 `State`、`Status`、`Result`、`Config`、`Capabilities` 还是 `Descriptor`
- `projector` 只说明“把输入映射成另一种表示”，没有说明产物、规则或业务意图；只有 projection 已是边界清晰的领域术语时才保留
- `xxxMap`、`xxxSet`、`xxxList` 等实现结构出现在业务边界
- 同一概念在 `Task`、`Job`、`Run`、`Execution` 等近义词之间漂移，或同一个词在不同地方含义不一致
- 只能靠注释解释真实含义；解释 `Mark` 的第一句总是“Mark 就是 finding”，应直接叫 `Finding`

### 命名纠结时

命名困难通常不是词汇量问题，而是当前解决的问题、对象边界或与相邻概念的差异还没有说清。按以下
顺序收敛：

1. 用一句话说明正在解决何种问题，并写出对象的 owner、生命周期、输入输出、关键不变量及与近邻概念
   的区别。
2. 选择名字必须承载的概念，再为每个概念选择团队已有的规范词；先搜当前仓库的模型、API、协议和
   调用点，避免为同一事物再造词。
3. 将问题句翻译成英文需求和领域术语，用 Web 搜索和 GitHub Code Search 查找实现同类需求的成熟项目。
   搜索“问题 + 角色 / 阶段 / 协议”，而不是只搜某个候选词或“naming best practice”；例如搜
   `sandbox snapshot restore`，而不是 `restore manager name`。
4. 阅读同类实现的核心模型、公开 API、状态枚举、错误名及调用点，观察一组词如何共同表达边界；README
   的营销用语和单个符号的词频只能提供命名灵感，不能作为结论。
5. 比较 2–3 个边界相近的实现，记录每个候选词包含和排除的语义。优先采用已有行业术语；若对象边界
   不同，增加真正有区分度的 owner、阶段或规则词，不机械照抄。
6. 把候选名放回真实调用处朗读，并用相邻 case 和反例验证。若每个名字都别扭，回到第一步调整模型或
   抽象边界，不用更长的名字掩盖问题。

局部临时变量能直接表达意图时，不必进行一轮行业调研；这套流程用于领域对象、状态、接口和会进入多处上下文的核心概念。

### 用类比生成候选词

类比可以显化抽象角色和关系，但只用于辅助建模和生成候选词。先把真实对象、owner、生命周期和关系逐项映射到类比，再提取词汇；翻译回领域词更清楚时，最终代码使用领域词。

若相邻需求需要不断制造牵强角色，立即放弃类比。同一领域不要混用多套隐喻；只有团队无需反复解释，且类比能稳定覆盖主要变化方向时，才让隐喻进入公开命名。

### 自检问题

- 这个名字描述业务意图，还是描述当前实现手段
- 只看声明和调用点，人或 LLM 会对 owner、动作、阶段、单位产生正确预期吗
- 同一概念是否在仓库中使用同一个词；这个词是否又被用于另一种概念
- 去掉 `runtime`、`info`、`context`、`manager`、`projector` 等泛词后，还剩下什么真实语义
- 如果实现从 map 换成 DB、从 HTTP 换成 RPC，这个名字还成立吗
- 完整使用表达是否清楚，还是重复语境，例如 `http.HTTPServer`
- 同类开源项目如何命名这个问题；它们的对象边界是否与当前一致
- 如果名字来自类比，新增相邻 case 时映射是否仍自然

## 文档与写作

文档把作者脑中的问题模型转换成读者能够理解、检查和继续推理的共享模型。先判断读者已经知道什么、
此刻要解决什么问题、读完后需要作出什么判断或行动，再选择抽象层次与详略；术语正确只是基础，
表达还应让读者理解核心概念、因果关系与取舍。

内容放在哪里，还取决于稳定性和获取成本：越稳定、越需要跨文件或跨决策才能理解的信息越往上放，
越易变、越容易从代码直接读出的事实越靠近代码。

### 分层模型

| 层级 | 读者及其任务 | 适合承载 | 不应承载 |
|---|---|---|---|
| `README.md` | 判断项目是否适用、准备使用或接入的人 | 产品定位、问题边界、核心能力、核心概念与最短使用路径 | 内部生命周期、实现边界、源码地图和详细接口 |
| `AGENTS.md` | 准备修改项目、需要定位职责并遵守约束的开发者和 agent | 项目定位、代码地图、长期边界、关键约定、References 索引 | 流程展开、字段参数、阈值、例外分支 |
| `docs/<feature>.md` | 需要理解机制、评估取舍或演进设计的开发者与评审者 | 理念、概念、主流程和关键设计的 why，可点名少量模块作锚点 | 跟着代码频繁变化的实现形状 |
| 意图标记（如 `spec` / `case` / `why` / `ideal` / `tmp` / `rule` / `link`） | 修改代码并追溯其依据的人和 agent | 贴近代码的契约、验证场景、设计理由、理想形态、临时措施及可选退出条件、维护约束，以及到相关资产的可寻址关系 | 长篇原理、没有稳定目标的自由文本、只靠标记保证的高代价约束 |
| 代码注释 / docstring | 修改或调用局部代码的人 | 隐式约束、顺序依赖、调用契约、易错场景 | 对代码表面行为的复述 |
| 代码 | 所有实现读者 | 字段、参数、阈值、分支和当前实现 | 需要跨文件或跨决策才能恢复的设计意图 |

### README 面向使用者

README 帮助读者建立使用模型：项目解决什么问题，输入与结果是什么，哪些约束决定是否适用。
使用者可能也是资深程序员，但不能默认他知道本项目的内部术语与实现历史；保留影响接入判断的技术
细节，省略此刻不影响选择与使用的机制。按读者认识产品的顺序组织，不默认以源码模块、命令层级
或内部 workflow 作为主线。
领域概念进入 README 时，要说明它向使用者提供什么、又要求使用者提供什么，不能只给出架构定义。
只有在能帮助使用者预测产品行为时，才用短小的数据流或控制流串起概念；内部生命周期、实现边界和
设计取舍下沉到 `AGENTS.md` 或设计文档，不把 README 写成目录清单、接口参考或实现说明书。

推荐按“4 个必选 + 1 个可选”的读者问题组织章节，标题可按项目语境调整，短项目也可合并相邻章节：

1. **定位与价值**：这是什么，为什么需要它。
2. **核心能力**：它能解决哪些问题。
3. **核心概念**：它如何理解和处理使用者的场景。
4. **快速开始**：如何安装、配置并完成第一次有效使用。
5. **扩展或深入阅读（可选）**：项目确实支持扩展或面向二次开发时说明扩展方式，有必要的深入材料
   时提供入口；不要为无法扩展的 CLI 凭空制造扩展章节。

### AGENTS.md 保持高密度

AGENTS.md 帮助准备动手的人恢复工作模型：改动属于谁、哪些边界不能破坏、到哪里找依据、如何验证。
高密度意味着留下决定行动的信息，并说清约束的理由；不能用术语缩写和路径堆叠代替解释。

- 围绕 `项目定位与边界`、`代码地图与核心模块`、`关键约定`、`References` 组织；已有文件优先渐进式收敛，不为格式统一而整体重写。
- 代码地图默认使用 tree 风格代码块表达目录层级，并在目录或关键文件行尾写明职责和所有权；路径只作为定位锚点，不代替能力描述。只有不强调层级、确实需要横向比较多个属性时才使用表格。
- 把关键约定控制在少量长期稳定、跨实现且不能破坏的模型、边界或依赖；合并同源规则。
- 每个设计点用一两句话说清“有这件事、为什么有”，详细说明通过 References 下沉。
- 使用仓库内相对路径；命令中的仓库根目录使用 `<repo_root>` 等占位符，避免写入个人机器路径。

### 设计文档解释 why

设计文档帮助读者复原推理：原始问题和约束如何导出当前模型，关键取舍解决了什么，又付出了什么代价。
从具体场景进入抽象，说明抽象保留了哪些共同结构、在什么条件下成立；让读者能判断一个新场景是否
适用。跨领域类比应交代对应关系和边界，抽象层次的提升要帮助解释或决策。

优先采用三段式：

1. **理念 / 概念**：定义核心词汇、对象语义和它们之间的关系。
2. **流程**：从触发点到结果描述主链路，只点名帮助定位的关键模块。
3. **关键设计**：每节回答一个“为什么这样做”，说明边界和主要取舍。

描述当前系统成立的模型，默认以绿地视角直接写最终状态：说明现行概念、协议、owner 和边界，不按实现时间写“第一阶段 / 第二阶段 / 后续”，也不写“旧字段已删除 / 不再兼容 / 从 A 迁到 B”这类迁移叙事。只有历史背景仍会约束当前决策时才保留，并压缩成“现行约束 + 原因”；迁移步骤和版本差异放在变更单、MR 或发布计划，不进入长期设计文档。不要把字段路径、固定阈值和 case-by-case 分支搬进设计文档。

`docs/` 下的设计文档只保留能为稳态模型提供独立信息的内容。若一句话能由已有的正向定义自然推出，不再补充对应的否定、防误解或边界重述，以减少重复和累赘。

#### 可选的 docs/kernel.md

当多个功能共享一套稳定的核心分层、执行模型和扩展边界时，可以用 `docs/kernel.md` 描述项目内核。
它展开的正是 [系统 = 核心概念 + 主流程](../SKILL.md#按语义变化控制设计深度)：核心概念是什么、如何协作，
以及支撑这套模型的边界与设计理由：

- 内核负责什么、不负责什么，以及它与业务扩展或外部适配的边界。
- 核心模块的分层、依赖方向和主要生命周期。
- 跨功能复用的控制流、数据流、扩展点和信任边界。

由 `AGENTS.md` 简要说明内核存在并链接到它，各 feature 文档只描述自己的领域差异。若项目没有独立、稳定且被多个功能共享的内核模型，就不要为了文档目录完整而创建 `kernel.md`；也不要把它写成源码目录索引或所有功能文档的合集。

### Blog：表达思路与协作改稿

#### 组织思路

1. **确定主线**：先确定读者、文章主旨和本篇要回答的问题。背景与已有文章负责铺垫，介绍产品时先说明它是什么、
   用户怎么用，再讲少量实现并带出优势，最后用案例落地；避免背景之后突然堆出组件名和内部调用链。
2. **实现带出价值**：每个设计说明它解决什么问题、给使用者或开发者带来什么能力。某项重要特性
   不自动成为全文主旨；深入机制可以留给配套文章。
3. **控制概念密度**：新术语随场景引入；已发表文章用简短回顾和链接承接，不重复展开整套理论。保留作者的表达习惯，
   用具体工作场景解释设计动机，不把文章改成接口手册或源码导览。
4. **安排例子**：伪代码放在最能说明开发能力或实现思路的位置，并标明省略和示意；案例章节可以侧重截图、视频和
   使用效果。同一个案例在不同章节承担不同作用，避免重复讲同一流程。
5. **使用配图**：架构图帮助读者理解关系，截图和视频展示实际体验；素材尚未准备好时保留占位符，不编造效果或证据。
6. **适当使用 list**：并列观点、能力或职责用无序列表，步骤和阅读顺序用有序列表；每项聚焦一个要点。
   动机、因果和过渡保留连贯段落，避免把整篇文章拆成清单；列表前留空行。

#### 占位与修改标记

每轮先读取作者当前文件，以手动修改后的版本为准。已有稿件默认保留原文；未明确要求直接改写时，
补充与删改采用以下可审阅标记，便于作者逐项取舍：

- **补充**：用 Markdown 斜体 `*补充内容*` 标记新增文字，包括新增标题和过渡句；多段补充分段
  标记。代码块等不能整体呈现斜体的素材，在块外用 `*补充开始*`、`*补充结束*` 标明范围。
- **建议删除**：用 `~~建议删除的原文~~` 保留原句并标记删除线，不直接移除。建议替换写成
  `~~原文~~ *建议的新文字*`；代码块等不适合行内删除线的内容，在块外说明删除建议并保留原块。
- **素材占位**：使用 Markdown 引用块 `> TODO：补充什么素材，用来说明什么`，让待补项在预览中
  也清晰可见，例如 `> TODO：插入 Router 页面截图，展示目标选择和处理详情。`。引用块前后留空行；
  沿用已有作者署名格式。缺失链接也用此方式占位，实际地址确认后再补 Markdown 链接。
- **只重组**：用户要求移动已有文字但不改措辞时，整段移动，保留原句与代码；新增衔接仍用斜体。
  不顺手修正错字、术语或伪代码，发现问题单独指出。
- **应用修改**：用户明确要求直接修改或接受某项建议后，只在授权范围内应用；不要一并清理其他待定
  标记。要求“看下、理解、给建议”时先在回复中反馈，不因标记约定而自动写入文件。

示例：`~~平台能够处理所有业务。~~ *平台提供公共运行能力，业务通过扩展表达自己的流程。*`

### 贴近代码的文档

#### 意图标记连接代码与文档

意图标记可以理解为**绑定到代码 symbol 的结构化注释**，更准确地说，是结构化意图注释。它保存那些
无法仅从实现稳定还原、但修改代码时必须理解的诉求；与代码共置，同时比自由文本注释更有类型、更容易
搜索、追溯和机检。它何时值得存在、应绑定哪个 symbol，以及 `spec` / `case` / `why` / `ideal` / `tmp` / `rule` / `link` 如何
分工，详见 [结构化意图标记](mark.md)。

#### 注释区分维护者与调用者

- 在函数内部用行注释解释只在局部实现内成立的 why、非显而易见的顺序依赖和容易被误改的约束；
  需要绑定到稳定 symbol、供后续修改追溯或机检的设计理由写成 `why` mark。
- 在类或公开方法的 docstring 中说明调用契约、参数语义、使用约束和易错场景，让调用方无需打开实现即可正确使用。
- 日志也是一种运行时注释：对关键状态变化、设计决策的真实动作和异常分支，用低噪声、无敏感信息且带上下文的日志记录 why，可同时服务代码理解与运行观测。
- 不复述函数名、类型和语句已经表达的 how；实现演化史不堆进 docstring。

### 落笔前自检

1. 代码一改，这段文字是否必须同步？若是，优先放进注释或代码。
2. 只看代码能否直接拼出这条信息？若能，不放进 `AGENTS.md` 或设计文档。
3. 是否必须跨多个文件或多次决策才能理解？若是，才值得进入高层文档。
4. 这条内容是在解释能力和边界，还是只罗列目录、字段和参数？后者下沉。
5. 文档是否便于扫描？
   - 一个段落只表达一个中心意思；出现多个并列判断、步骤或例外时，拆成列表或小节。若一句话需要
     用分号串联超过三个相对独立的逻辑，也按同样原则改写为 Markdown list，避免读者在长句中自行
     拆分结构。
   - 同时说明三个及以上的默认行为、配置规则、兼容策略或例外时，优先用一句引导语加 Markdown
     列表，不用逗号、分号把它们串成一个长段落。
   - 每个列表项只承载一个主要判断；某项内部仍有多个独立规则时，继续拆二级列表，不把长段落
     搬进一个 bullet 就算完成整理。
   - 同层列表项保持相近粒度；某一项明显更复杂时，保留该项作为主题，再用二级列表展开。
   - 用嵌套表达真实层级，但不为追求“短”把每句话都切成孤立 bullet。
6. 文档组织是否仍反映当前核心概念、流程和 owner，而不是按需求到达顺序持续堆叠？批量需求后的整理见[MR 序列复盘](evolution.md#mr-序列复盘)。
7. 文档是否已经过长？单文件接近 300 行时先删重复、细节和迁移叙事，再考虑拆分。
8. 删除“旧 / 新 / 阶段 / 后续 / 兼容”这类时间标签后，文档能否仍以现行模型自洽？若不能，先把稳态契约写完整，再决定是否确有必要保留历史原因。
9. 读者能否用自己的话复述核心模型，并据此判断一个相近但不同的场景？若只能重复术语，检查是否
   缺少概念间的关系、成立条件或具体例子；不必为此增加整套教程。
10. 详略是否服务于当前任务？README 应帮助判断是否适用并开始使用，AGENTS.md 应帮助定位改动与约束，
    设计文档应帮助评估推理和取舍。删减枝节时保留决定结论的条件，补充细节时说明它如何影响判断。

## 注释解释 why，不复述 how

- 注释优先解释为什么要这样设计、这样约束，帮助后来者理解决策背景和不能轻易改动的原因
- 少写或不写代码表面上已经能看出来的实现步骤，因为 `how` 往往更易随重构和实现调整而过时

## 契约、设计理由与临时措施

- 修改行为契约、领域不变量、非显而易见的设计原因或容易被误改的约定时，判断是否应把契约写成
  `spec`、把稳定设计理由写成独立 `why`，并绑定到真正拥有它的 symbol；不要标记可从代码直接读出的
  事实，也不要为了完整性强行补 `case`
  （见 [结构化意图标记](mark.md)）。
- 当前实现确因既有限制而将就，且已有稳定的绿地目标时，用 `ideal` 记录摆脱限制后应收敛到的形态；
  `ideal` 不是 TODO、排期或路线图承诺。
- 临时措施用 `tmp` 标明当前做法，退出条件明确时可补 `until`，避免把过渡实现误当长期设计；
  移除前需要依据，有 `until` 时先确认条件成立，详见 [结构化意图标记](mark.md)。

## 日志和错误必须能还原现场

- 日志和错误必须说明：在做什么、哪个对象/参数出问题、关键值是什么
- 只写“failed”“invalid param”这类信息，等于把排障线索主动抹掉
- 返回 error、异常、错误码都可以，但问题必须透明

## 格式服务于理解

- 用空行切分语义块，不要把多段逻辑压成一坨
- 高概率分支优先返回，减少无谓嵌套
- `if-return` 的卫语句通常比冗长的 `if-else` 更易读
