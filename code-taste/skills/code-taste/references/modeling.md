# 模型：业务概念、关系与流程

## 业务架构

这里聚焦业务架构中的 domain model（领域模型）与业务流程：**核心概念 + 关系 + 主流程**。业务指系统所服务的问题域，基础设施和开发工具也有自己的概念、规则与流程。业务概念的边界不自动等于服务边界；概念由哪些服务或模块承担，要结合 [职责与协作](modularity.md) 判断。

本篇判断模型是否足以表达需求；服务与应用内部如何分工见 [模块化](modularity.md)，如何审视现有设计并安排调整见 [演进](evolution.md#从问题到调整)。每个系统应能用一句话串起核心概念与主流程，并随需求演进校准。

概念承载稳定的身份、事实与规则，流程描述概念如何协作完成目标。进入局部实现后，再用“程序 = 数据结构 + 算法”检查表达与行为。只有概念没有流程，得到的只是词汇表；只有流程没有
概念，业务规则就会散落在条件、参数和胶水代码中。两者共同组成系统的最小充分模型。

概念也是约束的落点：系统级约束落实到拥有协调职责的概念及其协作契约，细节约束落实到所属
子概念的规则与不变量。明确约束由谁维护，再通过类型、状态转换或统一判断入口兑现，避免各流程
分别记住并重复实现同一规则。

系统的核心原则和约束应显式体现在概念的契约（如方法、关联）或主流程上；若必须追踪调用链、
分析实现细节才能发现这种关键联系，就是架构层的坏味道。应先检查是否缺少显式契约或统一流程，
而不是仅靠补注释解释隐式联系，也不为此堆叠新概念。

这里的“核心”始终相对于当前讨论的**系统边界与概念层级**：先声明从谁看系统、边界两侧交换什么，
再选择这一层的顶层概念；不要把内部对象、协议变体与边界概念全部平铺。一个对象在某层可以只是上位
概念的细节，进入它自己的子域后又可以成为该层的核心概念。

例如从 Baton Core 与 Harness 的边界看，Harness 的 `Input` 与返回的 `Event` 是顶层概念；`Event`
内部还可分正常吐字、tool、权限申请等变体，但这些属于 `Event` 的内部模型，不与 `Input`、`Event`
平级。只有把 Event 处理本身作为一个子系统展开时，才重新判断哪些变体值得成为该层的核心概念。

收束顶层概念不等于把内部复杂性压成少数几个字段或分支，更不否认需求与细节的多样性。大概念负责
给复杂性确定 owner 和边界，通常可以对应一个代码目录或模块；讨论整体架构时让它们少而清晰，讨论
边界内的局部需求时则允许并应当设计小概念、类型与流程，只要它们留在所属大概念内，不越级占据
全局心智模型。

## 识别概念、关系与主流程

沿当前问题涉及的业务链路，说明：

1. 核心对象是什么，身份、归属与关键关联如何确定；
2. 哪些事实、规则和不变量由哪个对象或流程负责；
3. 创建、复用、更新、回收等生命周期如何衔接，谁拥有转换的决策权；
4. 概念如何协作完成目标，输入、结果与失败恢复由谁承接。

据此判断问题属于既有模型下的实现细节，还是缺少概念、关系或流程。模型已能自然表达需求时，继续检查 [服务与应用内部的职责和契约](modularity.md)；反复依靠特判才能表达同一份身份、归属或生命周期时，检查下面的概念边界。

## 什么值得进入模型

概念候选来自领域常识，边界则由真实需求与演化校验：回看哪些事实、规则和生命周期反复共同变化，
把它们交给同一个 owner。划分概念既是为了分治、降低理解成本，也是为了让大多数日常需求能在一个
领域内完成；若普通改动经常牵动多个领域，应检查边界是否切错。变化局部性是复核方向，不是硬性比例，
跨领域协作本身也可以是系统的正常主流程；小程序的概念可由函数和类型承载，不要求搭完整分层。

- 重要业务逻辑必须显性化，体现在模型、命名、边界和接口上。关键规则如果只能靠读实现细节才能看出来，
  说明设计失败。
- 业务实体应同时承载关键业务数据和关键业务行为，避免只有数据没有行为的贫血模型。
- 模型是对稳定业务规律的压缩，不是把每个数据结构都升级成业务概念。
- **概念**回答系统里“什么东西长期存在、由谁负责、遵守什么规则”；通常有稳定身份、owner、
  生命周期、不变量或跨流程契约，值得进入核心词汇、公开接口或模块边界。
- **实现细节**回答“当前怎样实现或观察这些概念”；字段、事件、持久化记录、索引、Adapter、
  Viewer 投影和辅助类型都可以被明确命名、独立测试，但不必因此成为核心概念。
- 每个一等概念都会增加认知、命名和演进成本，必须比它引入的复杂度压缩更多事实和决策。
  如果新名词只是在替换一句实现描述，或其生命周期完全附属于已有对象，就留在实现层。
- 升级判断：删掉这个词后，多个流程都无法准确表达同一份身份、归属、生命周期或契约，且代码开始
  用重复特判补洞，才说明它应成为概念。反之，若它可由已有事实推导、只服务单条路径，或替换实现
  不会改变业务语义，就应继续作为细节。

例如 `Execution` 可以拥有一次运行的生命周期，而 `execution_end` 只是记录该生命周期结果的事件；
Prompt Snapshot 只是对运行记录的 Viewer 投影，不需要与 `Execution` 平级。

## 从发散到收敛

- 新 case 不等于新概念。新增名词前，先比较身份、所有权、生命周期、不变量和对外契约。
- 复杂模型先沿真实数据流发散组成、边界与候选 case，避免被首个方案限制而遗漏关键约束；发散用于
  扩大考虑范围，不代表每个 case 都要立即进入核心模型。
- 收敛时依据当前阶段的真实需求、发生概率、失败代价与未来补充成本，只保留最小充分模型。低概率且
  可局部演进的 case 暂不增加复杂度；低概率但高破坏、难以逆转的约束仍应保留。
- 最后用一条端到端链路复述模型；无法说清每个概念由谁产生、被谁消费，以及为何不能被相邻概念替代，
  说明模型还没有收稳。

## 选择收束形态

收束不等于强塞进同一个类，按差异强度选择三种方法：

1. **判别联合**：有限且稳定的变体，用 `kind`、`source`、`mode` 等真实业务字段分型；差异字段留在
   各自 variant，避免摊成大量 optional。
2. **接口 / 子类**：共享调用契约，但实现会独立演进或持续扩展时，用接口、Protocol 或抽象类收编；
   抽象表达共同语义和约束，不为复用几行代码制造空基类。
3. **领域 / 模块**：对象的身份和生命周期确实独立，不能合成一种类型，但共享更高层的 owner、边界、
   依赖方向或变化原因时，保留各自类型并收进同一领域命名空间 / 目录。领域不是杂物筐，必须能说清
   统一入口或边界，以及哪些依赖允许进出。

只有对象既不能共享类型 / 契约，也找不到共同上层 owner 时，才提升为顶层平级概念。共享几个字段
不足以证明该抽象，共处一个调用链也不足以证明该分域。

例如多种来源通过同一协调边界进入系统时，可以先收束为 `Input`，再按
`source = user | monitor | external` 分型；用户输入内部还可按
`kind = prompt | control | interaction_resolution` 分型。Adapter、Target、Session 不能合成
同一类型，却共同属于 Harness 执行边界，就收进 `harness/` 域而不是与 Input、Controller 平铺。

## 概念与流程的代码落点

核心概念通常由 interface、protocol、struct / class 等符号表达；承载身份、粒度、生命周期或策略选择的核心常量与配置，也是设计的落点。主流程由拥有协作顺序与生命周期契约的函数、方法或编排入口表达。

概念由哪些模块承担、目录如何组织，见 [代码与目录地图](modularity.md#代码与目录地图)；概念、流程和设计理由如何形成可阅读的文档，见 [设计文档与概念地图](expression.md#设计文档与概念地图)。
