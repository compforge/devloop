# 模块化：边界、分层与协作

本篇将 [业务概念与流程](modeling.md) 落到两个尺度：系统架构关注服务及外部依赖的职责与协作，Application Architecture 关注单个应用或服务内部的模块、分层和依赖。先确定问题涉及的边界，再安排改动；业务概念、可部署服务和代码模块之间不要求一一对应。

## 跨服务的职责与协作

单个应用与数据库、消息系统或外部服务之间也有系统层面的契约。涉及跨进程协作时，检查：

- **职责与数据 ownership**：谁维护权威状态、执行状态转换并承担生命周期责任？其他服务通过什么契约读取或请求变更？避免多个服务各自推断并修改同一份状态，却没有明确的协调规则。
- **通信 contract**：请求、响应与事件表达什么业务含义？身份、完成条件、兼容要求及错误语义是否明确？区分“已接受”与“已完成”，让消费方能正确判断结果。
- **一致性与失败恢复**：明确本地事务边界、跨服务状态何时一致，以及部分成功、超时或消息重复时由谁重试、去重、补偿或对账。只选择当前业务需要的机制，通信方式不能替代业务上的完成判定。
- **服务边界的收益与成本**：依据业务职责、独立演进、部署、扩缩容或故障隔离需求决定拆分；应用内部可以通过模块化解决的问题，不自动升级成跨服务拆分。服务已分开时，也不把职责或协议缺口藏进某个服务的局部补丁。

系统层面的契约明确后，分别在各应用内部落实职责；跨服务接口与本地模块接口的失败、延迟和一致性语义不同，不能只按调用形式类比。

## 入口、业务与机制

![入口、Service、Biz、Repository 与基础设施的职责关系](../assets/service-biz-infra.svg)

这张图表达 Application Architecture 中的职责分层。箭头表示可能的调用关系，虚线框强调按需提取的组件与边界；不要求每个业务经过所有方框，图中的 Service 是应用内的业务层，不代表独立部署的服务。

从应用内部的职责分层看，通常可以读作 **入口 → 业务概念与流程 → 底层机制**：入口承接触发，业务层表达对象、规则与协作，机制层提供与调用方业务无关的基础设施能力。这个视角说明业务由哪些代码职责协作实现，与 [业务建模](modeling.md) 互补。自下而上看，基础设施的资源与能力经业务概念赋予业务语义，再由流程组合成业务操作。

### 按职责分派改动

用上图安排改动时，先沿相关业务流程确认规则与数据需求的 owner，再检查各层契约是否足以支撑它：

| 职责 | 改动落点 |
|---|---|
| 协议输入、触发上下文与结果适配 | 入口 |
| 用例顺序、协作与业务规则 | Service / Biz；已有独立 Domain 时由其承接相应领域规则 |
| Command 执行所需的数据范围与访问契约 | Repository（如有）；否则由 Service / Biz 直接表达需求 |
| 纯 Query 的筛选、分页、排序与展示投影 | 查询 Service + DAO / Infra，通常不经过 Repository |
| 查询条件、持久化、外部调用等可复用执行能力 | DAO / Infra |

结合项目已有布局判断能力不足或职责错位；可以由多层协作修复同一问题，不必把改动塞进症状出现的方法。图中的组件按需存在，修复不以补齐层级为目标。多个调用方共用实现，也不意味着它们具有相同的业务需求或数据范围。

### 入口：承接触发

入口包括组装、启动与关闭的 `main`，以及 API handler、task 触发、MQ message handler 等操作入口。
入口 handler 负责处理协议与触发上下文，选择并调用业务流程；handler 保持薄，薄厚看职责而非行数：流式协议处理可以较长，但业务策略、资源归属与生命周期决策应由业务层承接。若新增入口需要复制这些决策，或普通需求总要在入口层跨域改状态，应检查是否缺少核心概念或统一流程入口，而不只是拆小 handler 文件。

### 业务概念与流程：表达规则并组织协作

入口形式不同，共用的领域规则与约束仍应由同一 owner 维护；核心概念与流程的识别见 [业务建模](modeling.md#识别概念关系与主流程)。

简单业务由一层 Service 承接即可。复杂业务可以按用例流程与内聚的业务能力分工；是否进一步提取独立 Domain，取决于领域模型及规则是否值得单独维护。

在常见的 Controller / Service / DAO 结构中，Controller 对应请求入口，Service 承接业务逻辑，DAO 承接基础设施中的数据访问。业务复杂后，可以从 Service 中提取业务组件（Biz）：Service 组织用例流程，业务组件封装内聚的业务规则与操作能力，并按职责访问所需的基础设施。Service 与业务组件共同构成业务层，都可以按职责直接使用 DAO、client 等基础设施，也可以为复用或控制复杂度进一步拆分内部组件；简单业务无需强行拆分。

此时，Service 可以形成相对通用的流程：**信息查询 → 调用业务组件 → 信息保存**。先取得相关对象及状态，将对象直接或经必要转换后交给业务组件，再根据执行结果保存状态。Service 负责用例约束、调用顺序和结果协调；业务组件负责具体能力，并通过不同实现承接执行差异。这是常见的流程骨架；业务组件也可以自行查询和持久化，具体归属与顺序由职责、事务、并发和故障恢复要求决定。拆分组件是为了明确职责，不要求各实现采用统一的中间对象或返回变更集。完整流程由组合这些组件的 owner 负责，组件各自完成被委托的职责。

### 底层机制：提供基础设施能力

机制层负责如何完成底层操作，并报告实际结果。它有自己的技术契约与资源生命周期，但不应认识调用方的业务对象，也不预设能力只能供某个业务域使用。提取通用能力时，检查接口是否仍夹带调用方身份、特殊路径或策略分支；这些语义由业务侧适配。

DAO 围绕自己负责的表与数据提供查询、增删改、条件更新等操作，承接 Service 与业务组件的数据访问需求。方法契约描述操作的数据、条件和结果，不预设由 Service、某个业务组件还是其他流程调用。调用方特有的业务策略，例如是否继续观测、哪些变化需要立即入库，应留在相应业务组件；DAO 负责执行数据操作及其一致性约束。通用性体现在按字段、条件、排序、分页等组织可复用能力，不以返回范围宽为标准，也不将某个调用方的业务策略写死在查询中。

### Repository：按需表达业务的数据需求

按 **CQRS（Command Query Responsibility Segregation，命令查询职责分离）** 区分两类用例：Command 执行业务规则并改变状态；Query 只读取和展示结果。这里的 Repository 只服务 Command 侧，包含执行命令所需的对象加载与查询；判断归属看用例目的，不能按是否执行 SELECT 划分。

纯 Query 通常由查询 Service 直接调用 DAO / Infra。页面展示常需要灵活的筛选、分页、排序、关联与字段投影，可以按查询需要组织读模型并返回 DTO，通常不需要 Repository。Command 与 Query 可以共用数据库和 DAO，按需要采用不同的读写模型。

Repository 的接口体现 Command 侧 Service / Biz 对数据资源的需求；实现负责把这些需求落实为 DAO、client 等基础设施调用，封装分页游标、批量读取、缓存访问、跨表 / 多 DAO 组合和必要的数据转换。它可以面向 DB，也可以面向外部资源或组合多个来源；接口围绕业务需要的对象和操作定义，不照搬底层 CRUD 列表。

DAO 与 Repository 的视角不同：DAO 围绕表与数据提供可复用的查询、更新和 CAS 能力，不预设调用者；Repository 从消费方所需的数据契约出发组织这些能力。接口通常靠近消费它的业务组件，实现按所依赖的基础设施安放；Biz 按接口取得所需数据资源，不必自行组织这些访问细节；不要求为每个表、组件或方法各建一套 Repository 或文件。

当 Command 的业务循环反复处理批次遍历、批量查找、缓存适配或多来源身份关联，导致核心逻辑难以阅读时，Repository 边界可以让业务只表达“获取所需对象，再执行规则”。候选范围、是否合并两侧身份、状态迁移与回收决策仍由业务 owner 决定；Repository 应落实明确约定的业务查询范围，共享加载工具不能擅自扩大它。

**规则归属与执行位置分别判断。**业务 owner 决定需要哪些对象，Repository / DAO 将可表达的筛选尽量落实到数据源查询，提供完成职责所需的合理最小数据范围；避免多个组件读取同一宽集合后各自丢弃无关数据。没有 Repository 时，Service / Biz 可以直接向 DAO 传递明确的查询条件。

必要范围首先关乎哪些对象需要读取，其次才是字段投影与批量大小。查询时收敛范围必须保持业务所需结果的完整性；单纯加索引、分页或任意截断结果，不能替代数据契约的修正。无法在数据源表达或依赖动态业务决策的筛选，可以在取得合理候选集后完成。案例见 [从宽查询追到消费方数据契约](examples/query-scope-follows-consumer.md)。

例如对账时，Repository 可以提供候选 keys 的懒遍历和按 key 批量读取；实现复用 LoadingSource 承接分页与查询机制。Manager、Observer、GC 分别选择 DB keys、实际资源 keys 或两者去重后的 keys，再执行各自的 reconcile。LoadingSource 是可复用的加载机制，Repository 是业务的数据访问契约，两者不等同。隐藏分页、缓存实现，不代表隐藏读取语义：缓存新鲜度、快照范围、缺失与失败的区别，以及写入的事务 / CAS 条件仍须明确。

**Repository 与独立 Domain 层都是按需边界，不是必经层。**简单场景可以由 Service / Biz 直接使用 DAO、client；只增加转发与跳转成本时不引入 Repository。领域规则形成值得独立维护的身份、状态转换与不变量时，再提取 Domain 模型及行为；不为分层齐全创建空壳 Domain，也不要求引入 Repository 时同步增加 Domain。已有的 Service / Biz 仍可按复用与复杂度进一步内部分工。

## 复杂度

- 架构的首要价值是控制复杂度，不是展示技术栈。
- 复杂度是增量引入的；每次改动都应减少混乱，至少不能继续放大。
- review 设计时追问：这会让系统更容易变更，还是更难变更？
- 模块持续增长到无法单独理解时，应按 owner、职责和变化原因拆分。长度是复核信号，不是架构目标；
  函数、参数和局部可读性的判断归 [代码 Review](review.md#代码评审流程)。

## 内聚性与共同演进

内聚性体现在一组代码共同承担一个完整职责：共享同一规则、状态约束或变化原因的数据与行为，应组织在
便于共同理解和修改的范围内。

- **共同演进的代码保持邻近。**当一项合理的需求变化必然涉及多处逻辑时，应缩短它们之间的理解与修改
  距离，让维护者容易发现关联，并能在明确的职责边界内完成修改。
- **边界应封装知识。**拆分后，如果两侧仍须了解彼此的内部状态、执行顺序和特殊约定，拆分可能只是
  拉大了距离。应考虑收回泄漏的知识、调整职责归属，或将相关实现重新聚合。
- **独立变化的职责保持分离。**共用数据类型、处于同一调用链或采用相似技术，不足以证明属于同一职责；
  将它们聚合需要共同的语义与变化原因。
- **联动修改是线索，需要追问原因。**共享规则带来的共同演进，与重复实现、内部细节泄漏造成的被迫
  联动，应区别处理；后者可能需要消除重复知识或修正依赖。
- **文件组织服从职责边界。**同一内聚单元可以包含多个方法和文件。按阅读、依赖和编译需要安排布局，
  判断拆分是否降低整体理解与修改成本，不以行数、方法数或文件数代替判断。

## 代码与目录地图

- 概念应落实到命名、类型、行为和统一判断入口；文件 / 目录用于表达确有必要的组织与依赖边界。
  一个概念可以由已有文件中的类型或方法表达，不要求每个概念都新增文件。具体取舍见
  [代码归属与文件组织](modularity.md#内聚性与共同演进)。
- **文档可以不读，结构绕不开。**目录本身应是概念地图，读者扫一眼包结构就能拿到模型。
- 同一目录出现七八个子目录或核心文件，且阅读者必须同时理解它们才能判断改动落点，通常说明缺上位
  抽象或分域。数量只是复核信号，不是硬阈值；共享 owner 就按领域目录收口，共享契约就提抽象，
  只有真是稳定平级概念时才保留平铺。
- 概念已经在文档中立住、实例却仍散在多个模块时，应按 owner 把它升级为结构级：
  **模块归属看事实 / 职责的 owner，不看文件当前物理位置。**
- 结构必须兑现概念层级：variant 放进上位类型，implementation 放进接口命名空间，领域对象放进
  领域目录。分域就是把文档级架构升级成目录级架构。

删掉概念说明后，读者仍应能从命名、类型与目录关系还原主要模型。代码与文档若讲出两套概念层级，先校正 owner，再同步 [文档地图](expression.md#设计文档与概念地图)。

## 依赖朝稳定方向流动

- 核心业务优先依赖稳定抽象，不依赖外部接口、框架、数据库和消息协议细节。
- 接口是业务抽象和耦合方式的结合点，接口设计比数据结构更重要。
- 判断边界时同时问：事实由谁拥有、生命周期由谁收口、哪一侧更稳定。
- 重要约束如何由结构、契约测试或运行时对账承接，见 [约束机制化](evolution.md#约束机制化)。

## 深模块优于浅模块

- 模块应能力强、接口少、语义清晰。
- 只包装一层调用却增加概念、参数和跳转成本的是浅模块。
- 默认把常见路径收敛在模块内部，特殊行为再通过有限扩展点暴露。

## 资源提供方保持领域纯粹

- Manager、Service、Repo 等资源提供方只管理自己的领域模型，不依赖调用方的 DTO 或外部模型。
- 跨模型转换由同时了解两侧的调用方负责；复杂且多处复用时提取独立 Adapter / Mapper。
- 资源提供方应返回自身领域对象，不提供 `to_xxx_dto()`、`to_external_model()` 等跨层转换。
- 检查顺序：提供方是否依赖调用方模型 → 转换是否应留在调用方 → 是否真的需要独立 Mapper。

完整反例与改法见 [资源提供方保持领域纯粹](examples/provider-stays-domain-pure.md)。

## 封装要提供行为，不要只搬运数据

- 对象应暴露有语义的行为，而不是一串 getter/setter
- 避免火车残骸式调用链，让对象自己完成与自身语义相关的事
- 对价格、ID、状态等有业务含义的值，优先考虑值对象封装

## 复用判断

- 写任何“看起来通用”的逻辑前，按成本递增勘探：
  1. 搜本仓同名 / 近义符号；
  2. 查框架、common 库、既有 utils 是否原生提供；
  3. 看同模块近邻是否已有契合的 helper 或模式。
- 能复用且语义契合就复用；已有语义或边界不同、复用会逼出模糊接口时才新写。
- 复用的目标是降低长期维护成本，不是短期少写几行。
- 区分真实重复和意外重复；意图不同的相似代码可以保持分开。
- 错误抽象往往比重复代码更糟，抽象失败时宁可退回明确重复。

## 识别共享知识，再判断复用

- 业务逻辑和控制逻辑混在一起，是最常见的复杂度来源
- Request/DTO/ORM 穿层传递，会让边界和依赖失稳
- 遇到重复时，先判断是不是同一概念，再决定是否抽取共享方法
- 守卫逻辑（参数有效性检查、空值处理）应放在实现侧统一处理，不在调用侧重复
