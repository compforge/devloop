# 评审：架构与代码

## 架构评审

架构 review 判断方案是否解决了正确的问题，以及模型、边界和依赖能否持续控制复杂度。它用于 T2
设计调整，展开受影响的业务模型、系统协作或应用内部职责；T1 在确认既有设计能承接需求后进入 [代码 Review](#代码评审流程)。T2 在架构结论成立后，仍需再做一次
代码 review，确认实现忠实表达了设计。

### 架构评审顺序

1. 还原原始需求和非功能性约束，按 [从问题到调整](evolution.md#从问题到调整) 检查方案是否解决正确的问题。
2. 检查 [业务概念、关系与主流程](modeling.md#识别概念关系与主流程) 是否充分，说明模型保留或改变的理由。
3. 按影响范围检查 [跨服务协作](modularity.md#跨服务的职责与协作) 和 [应用内部职责](modularity.md#按职责分派改动)：数据 ownership、通信与恢复责任，以及模块 owner、接口两侧与依赖方向是否承接业务需求。
4. 涉及结构取舍时，检查主要备选与选择依据；用典型实现者和真实长期场景复核扩展路径、变化扩散、恢复边界与兼容约束。
5. 检查重要约束是否已有适当的 [机制承接](evolution.md#约束机制化)，再进入代码 review 验证实现。

### 升级为架构 Review 的信号

以下信号触发复核；按 [设计变化定档](../SKILL.md#按语义变化控制设计深度)，确认需要改变关键概念、职责、边界或 contract 时再升级为 T2。

- 单文件长期接近或超过约 800–1000 行，尤其是 coordinator、service、handler 等流程文件时，通常说明
  多个概念、owner、生命周期或变化方向仍挤在一起；先检查这些职责是否需要重新组织，再决定是局部整理还是设计调整。
- 同一个行为维度在准备、执行、失败解释和产物生成等多个阶段反复 `if/switch`，通常意味着该维度尚未
  成为显式策略、后端或领域对象。
- 拆分后的模块如果仍要求调用方同时知道每条分支的前置、工具、错误和清理细节，只是把大文件换成
  更多跳转，没有完成概念提取。
- 行数本身不是 finding。生成代码、静态表、协议声明或单一内聚算法可以很长；finding 必须指出具体
  混合的职责，以及由此造成的变化扩散或错误风险。案例见
  [超大协调器缺失概念](examples/large-coordinator-missing-concept.md)。

### Findings 写法

- findings first，按破坏性排序；没有 finding 时明确说明。
- 每条 finding 指向具体模型、边界、依赖或生命周期，并说明会在哪个真实场景失效。
- 区分“当前已破坏的约束”和“未来可能更优雅”的建议；后者不要冒充阻断问题。
- 摘要按“原始需求 → 主要备选 → 选择及原因 → 主要改动 → 对既有设计的影响”组织。

### 架构检查清单

下面只放检查问题；原则解释回到各主题事实来源。

#### 问题定义

来源：[从问题到调整](evolution.md#从问题到调整)

- 核心问题是什么，是业务问题、技术问题还是混合问题？
- 非功能性约束是什么？
- 是否比较过至少一个备选方案？
- 是否已经识别既有模型、边界、查询键和生命周期？

#### 模型与概念

来源：[模型与概念收束](modeling.md)

- 新需求仍在既有设计边界内，还是已经说明旧模型失效？
- 核心业务模型和新增维度是否显式命名？
- 关键规则是否在模型和接口层显性化，而不是藏在流程代码里？
- 业务实体是否只有数据没有行为？
- 新概念是否压缩了多处事实或决策，还是只给字段、事件、记录或 UI 投影换了名字？
- 可推导、生命周期完全附属于已有对象的结构，是否仍留在实现层？
- 新名词应该是判别联合、接口 / 子类，还是领域 / 模块？
- 若决定顶层平铺，是否真的找不到共同 owner、契约或变化方向？
- 同一目录是否出现需要同时理解的七八个平铺项，暴露缺失的抽象或分域？
- 删除设计文档后，命名、类型和目录还能否表达相同概念层级？

#### 边界与依赖

来源：[边界与依赖](modularity.md)

- 服务与模块边界是否按 owner、职责和变化原因划分，还是把业务概念、服务和模块机械地一一对应？
- 跨服务的权威状态、通信完成条件、一致性与失败恢复责任是否明确？
- 是否用应用内部补丁掩盖服务间职责或协议缺口，或为解决内部模块问题而引入不必要的服务拆分？
- 需要共同演进的逻辑，是否集中在便于理解和修改的职责边界内？若修改会跨边界扩散，是合理的契约
  协作，还是内部知识泄漏？
- 业务编排、资源操作、协议或存储适配的职责是否清楚？
- Request / DTO / ORM / 外部协议对象是否穿透核心？
- 依赖是否朝稳定抽象流动？
- 常见路径是否被深模块收口，特殊路径是否只有有限扩展点？
- 资源提供方是否依赖了调用方模型？

#### 接口

来源：[边界与依赖](modularity.md)、[函数与参数](behavior.md#函数职责与抽象层级)

- 接口名是否体现业务意图，而不是底层技术动作？
- 参数是否只包含真正需要的信息？
- 换一种语言、框架或存储后，这个接口语义是否仍然成立？

#### 易懂性与扩展成本

来源：[边界与依赖](modularity.md)、[可维护性判断](modularity.md)

- 是否先明确目标实现者和典型任务，并让他正确完成该任务所需的必备概念、决策和修改点足够少且局部？
- 正确路径能否从统一入口、类型和邻近代码直接发现，还是依赖必须预先知道的隐式顺序或跨模块约定？
- 新增一个同类能力时，是否只需实现领域差异；公共准备、上下文传递、组合入口和资源清理是否由稳定
  框架承担？
- 同一能力既可独立运行又可被上游组合时，是否复用同一执行入口，而不要求能力实现者理解并维护
  多套调用路径？
- 新增的概念、接口和类型转换是否实际降低了实现者的知识与工作量，还是只让模型更精确却增加了跳转？

#### 演进与约束

来源：[演进与约束](evolution.md)

- 长期场景会新增哪些参与者、生命周期和恢复边界？
- 近期 MR 是否反复修补同一个缺失概念？
- 重要约束是否只有文档宣告，还是已有结构、契约测试或运行时对账？
- 机制强度是否匹配违反约束的真实代价？

#### 可维护性

来源：[可维护性判断](modularity.md)

- 改动是在降低复杂度，还是把复杂度藏进更多跳转和抽象？
- 超大文件是否混合了多个可独立命名的概念、owner、生命周期或变化方向？
- 多阶段重复出现的同一分支维度，是否应成为显式策略、后端或领域对象？
- 模块是否仍能被单独理解和测试？
- 模块能否被单独替换，还是边界外泄导致调用方必须一起变化？
- 新增相邻需求时，是进入既有模块 / 扩展点，还是必须修改多个老模块？
- 动手前是否勘探过框架、common、utils 与近邻实现？
- 重复是否真是同一概念，抽取后的接口是否比重复更容易维护？

## 代码评审流程

代码 review 判断实现是否正确、清楚且可维护地表达既定模型和行为契约。T1 直接使用本文件；T2 先完成
[架构 Review](#架构评审)，再检查实现。若问题必须调整关键业务模型、服务 ownership / 协作协议、应用内部职责边界或依赖方向才能
解决，将它升级为架构 finding，不在局部代码里打补丁掩盖。

### 代码评审顺序

1. 对照相关概念与流程，检查 [改动落点](modularity.md#按职责分派改动) 是否符合职责，再检查行为契约、边界条件和失败路径是否正确。
2. 检查命名、控制流和抽象层级是否让读者能直接理解意图。
3. 检查函数职责、局部依赖、封装与复用是否控制住复杂度。
4. 检查错误、日志和测试能否还原并约束真实行为。

findings first，按严重度或破坏性排序。每条 finding 指向具体代码和可触发场景，说明当前行为与预期
契约的差异；没有 finding 时明确说明，不用偏好性建议填充结果。

## 代码检查清单

### [正确性与测试](behavior.md#正确性与契约)

- 主路径、边界输入、失败路径和清理逻辑是否符合行为契约？
- 状态转换、并发、重试或超时是否会破坏不变量？
- 测试是否覆盖本次真正改变的行为，而不是只执行了代码？

### [命名](expression.md#命名)

- 类、函数、变量名是否直接表达意图？
- 是否充斥 `data`、`info`、`manager`、`processor`、`handler` 等宽泛词？
- 是否使用 `xxxMap`、`xxxSet` 等实现导向命名掩盖业务概念缺失？

### [函数与抽象层级](behavior.md#函数职责与抽象层级)

- 函数是否只做一件事，内部语句是否处于同一抽象层级？
- 是否通过布尔参数、行为枚举或过宽上下文切换多种职责？
- 是否存在明显可以提前返回却仍然嵌套很深的结构？

### [模块与依赖](modularity.md)

- 业务逻辑是否和流程控制、协议适配、存储细节混在一起？
- 是否有 Request、DTO、ORM 或外部协议对象穿透层级？
- 是否因复用过宽查询而让多个组件各自过滤？修复是否落实了 [消费方所需的数据范围](modularity.md#repository按需表达业务的数据需求)？
- 依赖是否朝稳定抽象流动；若不成立，是否应升级为架构 finding？

### [抽象、复用与封装](modularity.md#复用判断)

- 重复代码是否真的是同一概念？
- 抽取后的共享方法是否语义清晰，比明确重复更容易维护？
- 对象是否提供有业务语义的行为，而不是暴露数据让调用方拼装？
- 是否出现大量 getter/setter 或火车残骸式调用链？

### [日志、错误与可读性](expression.md#日志和错误必须能还原现场)

- 日志是否带操作名、对象标识、关键参数和值？
- 是否吞错、静默忽略失败或只返回模糊错误码？
- 不同语义块是否清楚，高概率路径是否优先返回？
- 是否存在过长链式调用、炫技式函数式写法或难读嵌套？
