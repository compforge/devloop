# 评审：架构与代码

## 架构评审

架构 review 判断方案是否解决了正确的问题，以及模型、边界和依赖能否持续控制复杂度。它用于 T2
设计调整，展开受影响的业务模型、系统协作或应用内部职责；T1 在确认既有设计能承接需求后进入 [代码 Review](#代码评审流程)。T2 在架构结论成立后，仍需再做一次
代码 review，确认实现忠实表达了设计。

### 架构评审顺序

1. 还原原始需求和非功能性约束，按 [从问题到调整](evolution.md#从问题到调整) 检查方案是否解决正确的问题。
2. 检查 [业务概念、关系与主流程](modeling.md#识别概念关系与主流程) 是否充分，说明模型保留或改变的理由。
3. 按影响范围检查 [跨服务协作](modularity.md#跨服务的职责与协作) 和 [应用内部职责](modularity.md#按职责分派改动)：数据 ownership、通信与恢复责任，以及模块 owner、接口两侧与依赖方向是否承接业务需求。
4. 涉及结构取舍时，检查主要备选与选择依据；用典型实现者和真实长期场景复核扩展路径、变化扩散、恢复边界与兼容约束。
5. 检查重要约束是否已有适当的 [机制承接](evolution.md#约束机制化)，再进入代码 review 验证实现。

### 升级为架构 Review 的信号

以下信号触发复核；按 [设计变化定档](../SKILL.md#按语义变化控制设计深度)，确认需要改变关键概念、职责、边界或 contract 时再升级为 T2。

- 单文件长期接近或超过约 800–1000 行，尤其是 coordinator、service、handler 等流程文件时，通常说明
  多个概念、owner、生命周期或变化方向仍挤在一起；先检查这些职责是否需要重新组织，再决定是局部整理还是设计调整。
- 同一个行为维度在准备、执行、失败解释和产物生成等多个阶段反复 `if/switch`，通常意味着该维度尚未
  成为显式策略、后端或领域对象。
- 拆分后的模块如果仍要求调用方同时知道每条分支的前置、工具、错误和清理细节，只是把大文件换成
  更多跳转，没有完成概念提取。
- 行数本身不是 finding。生成代码、静态表、协议声明或单一内聚算法可以很长；finding 必须指出具体
  混合的职责，以及由此造成的变化扩散或错误风险。案例见
  [超大协调器缺失概念](examples/large-coordinator-missing-concept.md)。

### Findings 写法

- findings first，按破坏性排序；没有 finding 时明确说明。
- 每条 finding 指向具体模型、边界、依赖或生命周期，并说明会在哪个真实场景失效。
- 区分“当前已破坏的约束”和“未来可能更优雅”的建议；后者不要冒充阻断问题。
- 摘要按“原始需求 → 主要备选 → 选择及原因 → 主要改动 → 对既有设计的影响”组织。

### 架构检查清单

按本次影响选取检查问题，原则解释见各主题链接。

#### [问题定义](evolution.md#从问题到调整)

- 原始需求与非功能约束是什么？现有模型、边界和生命周期中哪些仍成立？
- 哪些观察导出了方案选择，哪些仍是假设？主要备选的收益与代价是什么，什么证据会改变选择？
- 复杂度被消除、封装、转移还是推迟了？调用方、实现方与运维分别承担什么成本？

#### [模型与概念](modeling.md)

- 现有模型能否自然表达新需求？关键身份、规则、状态和生命周期是否有明确 owner 与行为入口？
- 新概念是否压缩了多处事实或决策，还是给可推导、附属的数据结构换了名字？
- 差异应由变体、接口还是领域模块承接？命名、类型与目录能否表达相同层级，避免无共同职责的聚合或平铺？

#### [边界与依赖](modularity.md)

- 服务与模块是否按职责和变化原因划分？内部模块化是否已足够，是否存在跨服务缺口被局部补丁掩盖？
- 权威状态、通信完成条件、事务范围与失败恢复分别由谁负责？
- 哪项策略需要保护，运行时调用与源代码依赖是否支持这一目标？接口和数据模型是否泄漏外部协议或调用方细节？
- 目标实现者能否从统一入口、类型和邻近代码完成典型任务，还是必须掌握跨模块的隐式顺序与约定？
- 新增同类能力时，公共准备、上下文传递与清理由谁承担？独立执行与被组合时是否复用同一执行入口？
- 新抽象是否减少了理解、测试和修改成本？是否查过既有能力，并区分共享知识与表面相似的代码？

#### [演进与约束](evolution.md)

- 哪些关键假设需现在验证，哪些实现选择可推迟？隔离与迁移成本、等待所得信息是否支持这一决定？
- 有依据的变化场景涉及哪些模块、契约、测试和发布单元？联动来自必要协作，还是内部知识泄漏？
- 方案通过哪些约束获得简化，排除了什么需求？谁保证约束成立，失效时如何调整？
- 近期 MR 是否反复修补同一概念缺口？约束的结构、测试或运行时机制是否匹配违反代价？

## 代码评审流程

T1 在确认既有设计能承接需求后，检查实现是否兑现契约；T2 先完成 [架构评审](#架构评审)。若问题
需要改变关键模型、ownership、协作契约或依赖方向，回到架构层判断，不用局部补丁掩盖。

按职责与正确性、局部可读性、验证证据的顺序检查。Finding 遵循上面的 [写法](#findings-写法)，
区分真实缺陷与个人偏好；无 finding 时明确说明。

## 代码检查清单

### [正确性与测试](behavior.md#正确性与契约)

- 主路径、边界输入、状态转换、并发、重试及失败清理是否兑现契约并保持不变量？
- 新增或替换实现是否保持前置条件、完成条件、错误、副作用与一致性保证？
- 测试是否验证改变的行为，而非锁定内部调用？真实适配器的关键语义是否有相应证据？

### [命名](expression.md#命名)与[局部表达](behavior.md#函数职责与抽象层级)

- 名字是否准确表达当前层次的职责，还是用泛词或实现容器掩盖了概念缺失？
- 函数是否职责单一、抽象层级一致？参数、上下文、分支和嵌套是否增加了不必要的理解负担？

### [模块、复用与封装](modularity.md)

- 实现是否遵守既定职责和依赖边界，避免业务规则、协议适配与存储细节混杂？
- 查询是否落实消费方所需的数据范围，而非让多个调用方分别丢弃宽查询结果？
- 共享实现是否具有共同语义，是否由对象行为或统一入口承接规则，而非调用方拼装内部数据？

### [日志与错误](expression.md#日志和错误必须能还原现场)

- 是否能从日志和错误还原操作、对象及失败原因，且没有吞错、重复日志或敏感信息泄漏？
